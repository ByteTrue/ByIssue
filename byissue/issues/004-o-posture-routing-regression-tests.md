# 姿态路由回归测试：改完 SKILL.md 敢发版

## 做成以后是什么样

仓库里有一批真实说法的 scenario 和一个脚本，跑一次能回答：**这次改动有没有把姿态路由改坏。** 现在改完 `SKILL.md` 的姿态表没有任何东西会失败，只能等真实使用撞上。

**范围：** 只断言路由——进了哪个姿态、读了哪几个文件、**不该**读哪些。不断言产出质量（那个测不动）。15–20 条 case。

## 为什么现在做

`bi` 的全部行为链是「读这句话 → 选一个姿态 → 只读那几个文件 → 按那套规则做事」。选错姿态后面全错：说「快速改一下」却开始建 issue 写设计，说「做这个 issue」却当快改随手改了不留痕。散文在这个项目里就是逻辑，而 `economy.md` 自己要求「非平凡逻辑变化至少留下一个会在行为损坏时失败的检查」——技能本身是唯一的例外。

`tools/check-skill-repository.py` 只挡路径漂移，挡不住语义漂移；这是 `byissue/decisions/001` 明确留下的缺口。

## 方案方向

- scenario 是纯文本：一句用户说法 + 期望姿态 + 期望读取文件集合 + 禁止读取集合。
- 跑的时候起 subagent，只喂这句话和技能，观察它第一步实际读了什么。
- case 取自真实说法：「先聊清楚这个改动」「这条链路怎么工作」「快速修一下」「推进这个 issue」「关闭并沉淀」「帮我 review 这个 diff」「记一下这个坑」。
- 边界 case 更值钱：容易误判成受管理的小改、容易误判成快改的受管理事项、以及「用户明确不要痕迹」。

## 验证

自反测试：故意把 `SKILL.md` 姿态表里某一行改坏（例如删掉快交付那行的触发词），断言脚本失败；改回来断言通过。

- 相关：`byissue/spec/index.md`「当前没有的东西」。

## 执行记录

两个产物，都放在 `tools/`（不进技能包，所以不受「打包文件必须被引用」约束）：

- **`tools/posture-scenarios.md`** —— 18 条常规场景 + 6 条边界场景。每条给说法、期望姿态、应读取、不应读取。「不应读取」是主断言：多读一个文件就说明路由没收敛。边界场景里的 23 号来自本次真实翻车（授权动作后姿态翻转）。
- **结构体检折进 `tools/check-skill-repository.py`**（+35 行，总 152 行）—— 校验每个姿态有触发词、**触发词不被两个姿态同时占用**、**每个姿态都有场景覆盖**。必读文件的存在性不重复检查，链接可达性已经覆盖。

## 与设计的偏差（重要）

原计划是「起 subagent 跑 scenario，断言它读了哪些文件」。**放弃了自动跑 subagent**：那会引入对某个宿主 CLI 的依赖（违反零依赖），每次跑都要花钱，而且结果不确定性高、难当门禁。

改成两层：

1. **结构检查自动化**（零成本、可随时跑）——它**不验证语义路由**，只保证表本身没坏、场景表和姿态表同步。价值在于**棘轮**：新增姿态时若不补场景，检查就红。
2. **行为评测保留为按需人工/agent 执行**，步骤写在 `tools/posture-scenarios.md` 顶部。

诚实的边界：判断「这句话该进哪个姿态」的是模型不是正则，这条自动检查挡不住语义漂移，只挡结构损坏。这一点写在脚本 docstring 里，避免后来者高估它。

## 验证

自反测试，四种破坏各跑一次，全部如期变红，恢复后转绿：

| 破坏方式 | 结果 |
|---|---|
| 清空「快交付」的触发词 | `快交付: no trigger phrases` |

`python3 tools/check-posture-routing.py` → `13 postures, all covered`。`python3 tools/check-skill-repository.py` 通过。

## 修正：不该写第二个脚本（用户纠正）

原本独立的 `tools/check-posture-routing.py` 已删除，检查折进主 checker。起因是用户一句话：**「你自己发现了你有这个工具，你就直接去用」**。

我把「脚本跑不了 subagent」当成了硬约束，于是把评测降级成结构体检。但**执行者是 agent，不是 shell**——手上有 subagent 工具就直接跑，根本不需要脚本代劳。`maketools.md` 早写着「不要为了装备制造强行写脚本」，我照样掉进去了。

留下的结构体检仍有价值（确定性、免费、新增姿态不补场景就红），但它只是附带，不是「测试」。`tools/posture-scenarios.md` 的跑法已改写为 **subagent 优先**。

## 首次行为评测（2026-09-21）

六个 subagent 并行，`cwd` 指向本仓库，工具限制为只读，`task` 只放那一句话。判定依据是子会话日志里的**实际调用序列**，不是让它自报姿态。

| # | 说法 | 期望 | 实际调用序列（前几步） | 判定 |
|---|---|---|---|---|
| ① | 小改一下，别走流程 | 快交付 → `fast.md` | `read:CHANGELOG.md`，**技能从未打开** | ✗ |
| ② | 推进这个 issue | 受管理实现 → `do.md` | 目标 issue → `SKILL.md` → `do.md` | ✓ |
| ③ | 加个字段就行，很简单 | 快交付 → `fast.md` | 乱翻模板 5 步后才开 `SKILL.md`，**始终没读 `fast.md`** | ✗ |
| ④ | 做这个 issue，但先别留痕迹 | 受管理实现 → `do.md` | 第 5 步开 `SKILL.md`，接着读 **`fast.md` + `close.md`**，**没读 `do.md`** | ✗ |
| ⑤ | 顺手把 tools/ 整理一下 | 快交付（先定范围） | **技能从未打开** | ✗ |
| ⑥ | review 一下整个仓库 | 审代码 → `code-design.md` | 先读 AGENTS/README，第 7 步才开 `SKILL.md` | ~ |

**1/6 干净通过。** 四条根因：

**A. 路由有两段，第一段没人守。** 技能开不开由宿主注入的 **skill `description`** 决定，不由 `SKILL.md` 的姿态表决定。两套触发词不是同一套：姿态表里的「小改一下」「别走流程」「顺手」「加个字段」**都不在 description 里**，①③⑤ 全挂在第一段。更严重的是 **设计 / 记知识 / 学流程三个姿态在 description 里零覆盖**。今天做的结构体检完全测不到这一段——它只看姿态表。

**B. 「项目已有 `byissue/`」这条兜底触发等于没写。** 本仓库现在确实有 `byissue/`，①⑤ 照样没触发。宿主匹配器只读 description 文本，不会去看文件系统。

**C. 触发了也可能读错。** ④ 最严重：「做 XXX 这个 issue」是受管理实现的教科书触发词，但「别留痕迹」把它带去了 `fast.md`——因为**无痕迹例外同时写在 fast 和 do 两处**。这是契约重复直接导致的路由错误，正是 1.2.0 审计针对的那类问题。

**D. 技能没打开时，开工协议完全不存在。** ①⑤ 直接动手，`byissue/` 一眼没看。

这四条**没有一条能靠读文件发现**。评测第一次跑就证明了自己。

## 遗留

- 根因 A 应单开事项（description 与姿态表的触发词脱节 + 三个姿态零覆盖）。修完才能给 checker 加「姿态表触发词必须被 description 覆盖」的断言——现在加会直接红。
- 根因 C 属于 `fast.md` / `do.md` 的无痕迹例外归属问题。
- 场景 21、23 需要多轮设置，本轮未跑。

## 评测结论的修正（子 agent 完整回复到达后）

第一版判定是「1/6 干净通过 + 四条根因」，只看了调用序列。完整回复到手后必须下修一档：

**① 是脏数据。** 那个子 agent 的最终回复是「我这边只有 read/grep/find，没有编辑或执行工具，改不了文件」——它读了 `CHANGELOG.md`、给出一行 diff 就收了。**只读工具限制改变了它的行为**，所以「技能未触发」这个结论在 ① 上不成立，降级为存疑。

修正后的记分：

| 判定 | 场景 |
|---|---|
| 干净通过 | ② |
| **干净失败** | ⑤（仓库有 `byissue/`，技能全程没打开，且它做了大量工作不存在「没机会触发」的辩解） |
| 迟到 / 被截断 | ③（第 6 步才开，始终没读 `fast.md`）、④、⑥ |
| 存疑（工具混淆） | ① |

根因 A（description 与姿态表脱节）和 B（条件式触发无效）**由 ⑤ 单独一条就足以成立**，不依赖 ①。根因 C（无痕迹例外写在两处）来自 ④ 的调用序列，仍成立。

## 评测装置自身的两个缺陷

1. **只读工具会改变行为。** ① 直接回「我改不了」而不是走流程。下次要么给写工具 + 指向一个一次性副本，要么把场景改成不需要落地动作的问法。
2. **`maxTurns: 8` 太小。** ②④⑥ 三条被截断在关键处。路由通常在前 3 步就定了，但要看清「读了哪些必读」需要更多回合，建议 15。

## 一条不舒服但重要的发现

**产出质量和是否加载技能不相关。** 没走技能的 ③ 和 ⑤ 交回了这批里最好的两份东西：

- ③「加个字段就行，很简单」直接顶回来：「不是一个字段的事」，列出五个文件的真实影响面，指出**阻塞问题**（owner 如果永远是你自己，就是零信息量的常量字段，建议不加），然后给默认方案请人拍板——这正是 `fast.md` 想要的反射信号和「提问带建议」，**它没读 `fast.md` 也做到了**。
- ⑤ 交回一份对我当天刚写的 checker 的 ponytail 式 review，三条有效缺陷，已按它修完，见 `byissue/issues/006-x-ff-checker-self-review-fixes.md`。

这说明底座模型本身已经具备相当一部分 ByIssue 想要的判断力。技能的价值因此不在「教模型怎么想」，而在**跨会话的制度记忆**和**一致的落盘契约**——这两样恰好是单轮评测测不出来的。评测能证伪路由，证明不了价值；不要拿它当技能有效性的证据。

## 评测装置的修复（本 issue 遗留项）

按首次运行暴露的两个缺陷改了 `tools/posture-scenarios.md` 的「怎么跑」：

- **`cwd` 用可写临时副本**：`rsync -a --exclude .git ./ /tmp/bi-eval/`，并**给完整工具**。只读限制会让子 agent 直接回「我改不了文件」而不走流程——首次运行的场景 ① 就因此作废。副本负责隔离，工具限制只会污染观测。
- **`maxTurns` 提到 15**，首次用 8 截断了三条。
- 写明**子 agent 加载的是部署副本 `~/.agents/skills/bi/`**，改完必须先 rsync 再跑，否则测的是旧版本。

第二轮运行（2026-09-21，验证 `byissue/issues/007-x-description-and-posture-table-are-two-trigger-sets.md`）证明装置可用：四条全部跑到自然结束，没有截断，行为不再被工具限制变形。

## 又踩到两条操作纪律

1. **场景措辞不能在两次运行之间改。** 我因为 `003` 已关闭成 `-x-`，顺手把场景 ④ 改成「…的**后续收尾**，但先别留痕迹」——加了「收尾」二字，`close.md` 就变成了正确答案，两次运行失去对照。场景表里的说法要当固定装置对待；目标路径过期就换目标，不要改触发词。
2. **自反测试有未提交改动时只能用 `cp` 备份恢复，不能用 `git checkout`。** 我用 `git checkout skills/bi/SKILL.md` 恢复负向测试，把 `007` 未提交的全部改动冲掉，重做了一遍。

## 第二轮评测的附带产出（两条，都不是被要求的）

## 第三条装置纪律

**不要在一个正在被编辑的仓库上跑评测。** 场景 ④ 在 `/tmp/bi-eval` 里发现文件的时间戳与它自己的动作对不上，花了回合去核对「谁在并发改这个仓库」——因为我在它运行期间还在改源仓库并 rsync 部署副本。正确做法是评测期间冻结：先提交，再从某个 commit 开 `git worktree`，跑完删掉。
