# 姿态场景全表在 DeepSeek 上的结果

> **读者：** 改 `skills/bi/` 之后重跑行为评测的人，以及想知道「弱模型照着 bi 做会在哪里掉链子」的人。

**结论：** 2026-11-09 用 `deepseek/deepseek-flash`（high 思考）跑了姿态场景全表、状态字母五臂和 1.13.x 的五个探针（压缩后接续 F1、无痕迹下说提交 F2、已有 Epic 的大任务 F6、spec 约束依据过期 F8、无痕迹的大任务 F9），共 41 条。前后修了六处文本，修后全部通过；表里每条都在 DeepSeek 上复测过，不稳定的跑了 3 次。弱模型的失败都是同一种形态：规则只写在 `SKILL.md` 的括号里、或者只是一个「（见 X）」指针，弱模型照着它当时读的那份姿态文件做，就会漏掉。修法是把动作写进模型当时正在读的文件，并写成祈使句。

**依据：** 2026-11-09 本机实测。夹具与计分脚本是 `tools/fixtures/posture_table.py`、`tools/fixtures/posture_judge.py`，可以重跑。路由判据来自子会话的工具调用参数，行为判据来自夹具的最终文件和 git 状态。用之前先复核：模型或技能文本变了，结果会变。

## 失败与修法

| 场景 | DeepSeek 做了什么 | 根因 | 修法 |
|---|---|---|---|
| F8：spec 约束依据的上游限流已过期，用户只说「弄快点」 | 改代码，并且没问就把 spec 约束从 100 次/分放宽成跟随上游 | `fast.md`、`complain.md` 只写「真相变了同步 spec」，没区分当前真相和约束；「先问」只在 `SKILL.md` 第 5 步的括号里 | 两份文件写明「要放宽或推翻 spec 里的约束，先问用户」，`fast.md` 还点名了「约束依据的事实过期」这一种。复测：先实测 540 秒，再停下来问，没动任何文件 |
| 30：把 `old/` 里的命令行工具全部移植到 `new/` | 先写完代码，最后才补 Epic 和台账 | `large.md`「开工前」列了五步，但没说做完五步才能动代码 | 「开工前」开头加一句：五步做完、spec 和台账写到磁盘上，再改第一行代码。复测：spec → 台账 → 代码 |
| 10：结账偶尔重复扣款，用户说 debug 半天没头绪 | 修对了根因（超时重试），但没读 `debug.md` | 场景表把按需读的 `debug.md` 写成了必读。另外 `complain.md` 的升级条款只是「（见 debug）」 | 场景表改成按需读；`complain.md` 改为「先读 debug「升级」，按它上完整手段」 |

| F8 复测第二轮 | 没有弹窗工具，就「先按推荐做了」并放宽了约束（同一场景上一轮是写完问题就停） | 「提问必须带建议」只写了怎么问，没写问完要停 | `SKILL.md` 加：要先问用户的事，问完就停在这一步；没有提问工具就把问题写在回复里，同样停下。复测 3/3 停住，工作区干净 |
| 12：关闭并沉淀 | 把 issue 正文当成「用户原话」写进 spec | `SKILL.md`「记录写给下一个 agent」只写了「引原话（拿不到就写明转述自哪份记录）」 | 改为：只有用户在对话里亲口说的才叫原话，来自记录的写明转述自哪份。复测通过 |
| 30：第二轮 | 顺序对了，但跳过 `do.md` 直接读 `large.md` | `SKILL.md` 大任务那一行只说「读取并执行 large」，没说主姿态是受管理实现 | 改为「主姿态是受管理实现，先读 do，动手前再读 large」。复测 3/3：do → large → spec → 台账 → 代码 |

审查（也在 DeepSeek 上跑）另外找出几处同一形状的问题并已修：升级条件在 `complain.md` 和 `debug.md` 各有一份且已漂移（改为只留 `complain.md`，`debug.md` 指过去）；`fast.md` 开头「违反时先改 spec（须授权）」与回写段的「先问用户」两种说法；`close.md` 关闭时「Project Spec 没有与实现冲突的旧表述」会让模型把放宽过的约束直接写进 spec。审查者要求补的两个评测也跑了：受管理 bug 碰到过期约束（先问，通过）；关闭一个实现已放宽约束的 Epic（改了 spec，但该 Epic 的已验收方案本身就是放宽后的做法，判为用户已同意）。

场景 30 原夹具的 `old/` 只有一个 21 行的脚本，DeepSeek 会合理地判断「一次对照就能确认」，不走 large，所以那个夹具判不出这条规则。现在的夹具里有三个工具、十几个子命令和一批选项。

## 通过但要知道的

- 大任务做到最后，DeepSeek 会把与旧版的行为差异按「改进」默认处理，然后列给用户定（场景 30：越界参数从崩栈改成报错、`--high` 写在文本后面会被当成选项）。用户要求的是「和旧版对齐」，这几处是在汇报里问，不是悄悄改。用户 2026-11-09 定为保持现状：先做、在汇报里问。
- 修 bug 时 DeepSeek 很少读 `debug.md`：最终文本上场景 10 跑 3 次读了 1 次，环境相关的夹具（日报测试本地 CST 绿、CI 的 UTC 红）1 次没读。但 4 次的行为都对：先复现，补一条在旧代码上会红的检查，修在根因。`debug.md`「升级」要的东西它不读也做到了，所以没有再加强这条指针；用户 2026-11-09 同意接受。
- 1.14.0 的探针又证实了一次「只照当前在读的文件做」：改状态脚本的三问放在 `code-design.md` 时，快改跑（P7）只读了 `fast.md`，脚本原地覆盖；整句移进 `fast.md` 和 `do.md` 后，两条路径（P7、P7D）都读到了，脚本改成先写临时文件再改名、重跑不变。所以同一条规则要在两个姿态文件各放一份同文，而不是一处原文加一处指针。
- 夹具源码太小时，模型读一遍代码就能定位，不会进 `debug.md`「升级」。P2（越用越慢）两次都是读源码看出二重循环，再计时证实，「先取 profile」那条没机会被测到。要测升级路径上的规则，夹具得让读代码定位不了。
- 会话中途重启会杀掉还在跑的子 agent，那些条目会只剩一半日志。用新的根目录重搭夹具，单独重跑。
