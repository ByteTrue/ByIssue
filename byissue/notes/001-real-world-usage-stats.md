# ByIssue 在真实项目中的使用分布（2026-09-21 实测）

> **读者：** 要决定「下一步改哪条规则」的人——先看分布，再决定优化谁。  
> 这组数字是人工统计四个真实仓库的 `byissue/` 得到的，产品本身不采集任何使用信号；想复现就重跑文末命令。

**结论：** 快改（`ff`）是绝对主路径（46%）；编号规则在高密度仓库里系统性失效（最高 14% 碰撞）；spec 的**分层**而不是毕业本身，是产品型项目的瓶颈。1.1.0 新加的 `decisions/` 与 `-d-` 目前**没有足够数据下结论**——别用全历史事项数当它们的分母。

## 何时用

决定要不要新增、修改或删除某条行动规则时先看这里。凭直觉排序会排错——下面每一条都推翻过一次静态判断。同时注意下面那条「分母陷阱」，它已经骗过一次。

### 分母陷阱（第一版结论在这里翻过车）

`decisions/` 和 `-d-` 是 **1.1.0（2026-09-17）才引入的**，只存在了四天。拿它们去除以 322（跨越三个月的全部事项）会得出「几乎零使用」的错误结论。

正确分母是这四天里新建的事项：

| 窗口 | 新建事项 | decisions | dropped |
|---|---|---|---|

**约每 7 个事项产出 1 条 decision，这个比例不低。** `-d-` 零使用在 22 个样本上说明不了任何事（放弃本来就该是低频事件）。这两个实体的结论是「数据不足」，不是「无人使用」。

另注：`created:` 日期本身不完全可信——AGCopilot 里有 2025-09、2026-10、2026-11 三个明显不可能的值，是写入时猜的日期。

## 站得住的四条发现

1. **`ff` 占 46%，而且它是健康的。** 均长 30–35 行，四答结构被实际遵守（样本里还自发长出「后续修正」「顺手发现」两节）。这条路径是成熟的，也是 WHY 里说的「下沉」最该指向的对象。
2. **编号碰撞 28 处，且随密度上升。** AGCopilot 168 个事项里 23 处碰撞（14%），一个 `087` 撞了四次。「取本树最大序号 + 1」在并行会话 / worktree 下不成立，而 agent 也不愿为了取号去 `ls` 一个 168 文件的目录。这是事项唯一的身份机制，它有 14% 是坏的。
3. **瓶颈不是毕业，是分层。** AGCopilot 的 spec 是单文件 311 行 20 个标题（内容本身写得认真：能力地图、使用路径、架构地图、统一语言），pi-package-mono 是 8 文件 867 行。同一套规则、两种形状：包库型项目有天然边界所以自己分了层，产品型项目全压进 `index.md`。`docs.md` 写了拆层原则，但没有任何东西会在「该拆了」的时刻提醒。
4. **notes 的正确分母也不是全部事项。** 13 篇 / 322 看着低，但大量 `ff` 是 UI 微调，本来就没有可沉淀的东西。值得沉淀的是「踩到了仓库外部事实」的那批——pi-package-mono 的 notes 几乎全在这个区间（`002-atomic-config-0o600`、`004-npm-workspaces`、`008-chromium-profile-login-state-primitives`、`009-reload-globalthis-pin-data-not-instances`）。要评估沉淀率，得先能识别这批事项。

## 怎么复现

```bash
for R in work/AGCopilot byspace pi-package-mono toolbelt; do
  D=/Users/zijie/workspace/projects/$R/byissue
  find "$D" -name "*-ff-*.md" | wc -l                          # ff 数
  ls "$D/issues" | grep -oE "^[0-9]{3}" | sort | uniq -d        # 编号碰撞
  find "$D/spec" -name "*.md" | xargs wc -l | tail -1           # spec 规模
  grep -rl "^created: 2026-09-1[789]\|^created: 2026-09-2" \
       "$D/issues" "$D/epics" --include="*.md" | wc -l          # 新实体的正确分母
done
```

**相关：** `byissue/spec/index.md`「当前没有的东西」；`WHY BYISSUE.md` 的认知负荷论证。
