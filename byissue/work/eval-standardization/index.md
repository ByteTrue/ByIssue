# 标准化 pi 评测并修复已观察到的工作流缺口

## 目标与边界

用户要求将上轮评测沉淀为后续的标准流程，并直接优化或修复评测暴露的问题。标准流程使用 pi、空项目中的实际安装副本、独立验收和阶段快照；本次以旧技能和修改版对照验证规则执行。

## 已定方案与约束

- 维护入口放在 `tools/evaluation/`，技能包仍独立分发。固定业务输入与验收从原评测提升为回归用例，历史记录保留。
- 运行器负责安装核对、会话隔离、业务验收、来源保护、日志与指标采集。动作顺序与 Memory 内容按 trace 和产物审查，不用关键词打分替代语义判断。
- 检查点修复归属 `SKILL.md` 的检查点协议；改变规则只引用该协议。要求变化时先单独写 work，再改变业务文件。
- Memory 修复归属 `memory-direction.md`：先判断跨工作用途及不可重建性，再记录符合条件的决定、外部事实或证明入口。模板同步提示未来判断与重访条件。
- 证据标签从实际命令与输出填写，覆盖上轮把 SHA-1 写成 SHA-256 的错误。
- 比较只报告本轮样例结果；时间、token 作为观测值，单次对照不支持普遍提效结论。
- 对照默认顺序运行。TMPDIR 只约定临时路径，严格文件系统隔离需要宿主支持。

## 证据与决定

旧评测来源为 `byissue/work/v2-readiness/evaluation/`。工具记录显示两轮都读取了相关规则；因此本次修复优先把规则绑定到具体写入时点，并收紧 Memory 的选择条件。根因解释是修订假设，后续对照只支持对应样例的改善。

首轮实测：修改版 ledger 第二轮在 trace 第 25、29 行先更新 work，第 32 行才改业务代码；两轮 Memory 为空。独立记忆场景保留了协议决定并把交接安排写入 work，但在 Memory 中自行增加“重试只重发失败记录”，超出用户确认范围。因此补充已确认范围规则，再跑同样输入；首轮结果保留。

第二版实测：Memory 正向场景三项通过。ledger 的检查点先写入也通过，但第二轮 report 输出为 `count=...` 与 `total_cents=...` 两行，独立验收因非 JSON 失败。追溯发现第一轮 work 将用户要求压缩为“汇总条数与总金额”，漏掉尚未实现接口的格式。补充的规则放在 prove 与 work 模板，保留所有原始输入与验收。

第三版实测：ledger 两轮业务验收与已列工作流判据通过，Memory 正向场景三项通过。全部修订、失败产物、工具记录与指标见 [evaluation](evaluation/README.md)。长期判定原则记录在 `byissue/memory/evaluation.md`。
