# 沉淀由 agent 直接落盘，每条记录写明后来者凭什么采用它

用户 2026-11-09 的原话：「所有该沉淀的地方，你在流程中就直接顺手沉淀，然后最后给个总结给用户，用户觉得有问题那就再改」，同时「提交推送关闭留给用户没问题，这是必须的，也是人在环的重要保证」。适用范围：长期，`skills/bi/` 的所有姿态。

据此定了两件事。第一，沉淀收割不再逐条请用户裁决：agent 查重后直接写进 `byissue/`，汇报里列出写了什么、写在哪。第二，提交、推送、关闭仍要用户开口，但说一句就够，按「沉淀补齐 → 毕业回写 → 关闭改名 → 提交 → 推送」的固定顺序执行到他说到的那一步。

沉淀自动化以后写进来的东西会变多，所以同时定了写法：每条记录分清它是用户原话（需求依据）、agent 的观察（调查线索，带日期、版本或环境和证据，用之前先复核），还是可以重跑的检查（直接重跑）；代码和 git 历史能回答的不写。这条取代 `byissue/decisions/009-quantified-claims-carry-their-evidence.md`：把它从量化判断推广到所有观察类记录，规则移进 `SKILL.md`。

## 背景

用户同一条消息里的原话：「问我是不是要沉淀，我都是回复'按建议沉淀'。而且每次干完我都是'按建议沉淀关闭收尾提交推送'，因为之前我不说全的话模型就有可能漏掉某个操作，比如先提交后关闭。」

以下是 agent 的判断。`byissue/talks/001-what-to-build-next-and-does-documentation-rot.md` 第 8 节要求沉淀候选带着建议问用户，当时担心用户累了会回一句「算了」。现在情况反过来了，用户每次都回「按建议」，这一步不再带来信息，只多一次往返。授权点又分散在几处，执行顺序要靠模型自己排。另一个可选做法是保留裁决、只把建议写得更好，但它减少不了用户出场的次数，所以没选。代价是写错的沉淀会先落盘、之后才被发现，靠三样东西兜底：汇报逐条列出、用户纠正、git 可以回退。

记录分三种用途的来源是 2026-11-06 讨论 v2 时的认识，见 `byissue/talks/2026-11-09-bi-v2-rejected-what-carries-over.md`。
