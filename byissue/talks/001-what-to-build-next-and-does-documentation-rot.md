# ByIssue 下一步做什么，以及文档到底该不该写 talk

> 2026-09-21。起点是「之后的方向应该做什么、有哪些不足」，收在一个比原问题更深的结论上。本文按讨论推进的顺序写，被推翻的判断留在它被推翻的位置。

---

## 1. 静态判断：三个不足，和一个我答不了的未知

我先只读仓库给了三条：没有行为回归测试（散文即逻辑，但改一句 reference 没有任何检查会失败）、不自举（ByIssue 自己没有 `byissue/`）、没有增长预算（唯一阻止技能膨胀的机制是人碰巧注意到）。

同时标了最大未知：**完全没有使用信号**，上面的排序全建立在静态判断上。

**已确认：** 先做自举；只建 `spec/` + `decisions/`，不建 Vision（愿景是 `WHY BYISSUE.md`，刚删过一份副本）；反馈回路只测姿态路由不测产出质量；增长预算不设行数上限，改成「新增规则必须声明唯一归属」；中文 only 暂时保持。

## 2. 实测四个仓库，推翻两条静态判断

用户给出 `work/AGCopilot`、`byspace`、`pi-package-mono`（外加 `toolbelt`）。统计 322 个事项，数据见 `byissue/notes/001-real-world-usage-stats.md`。

两条静态判断当场翻掉：

- 我以为「AGCopilot 168 个事项只有 1 个 spec 文件 = 没在毕业」。错了——那 311 行写得很认真。真问题是**没分层**。
- 我完全没看到编号碰撞：AGCopilot 14% 的编号被共用，`087` 撞了四次。**这条静态审计永远发现不了。**

## 3. 纠正：分母陷阱

我写下「322 事项 / 2 条 decision，三条件门槛等于关掉了这个实体」。

用户纠正：`decisions/` 和 `-d-` 都是 1.1.0（四天前）才加的。正确分母是这四天新建的 22 个事项 → 3 条 decision，**约每 7 个一条，不低**。

**最终以此为准：** 这两个实体的结论是「数据不足」，不处置。已回写 note 并把翻车过程留在原地。

## 4. 文档腐化：尺子换了

用户提出真正在意的问题：经验沉淀在实际使用中很少发生，而且「文档容易腐化、代码就是真相」的说法很有道理。

同意它对的部分——当天 ByIssue 自己的文档漂了四次（`done/` 残留三处、onboard 手抄目录清单漏 `decisions/`、WHY 的实体清单停在「三个核心实体」、我刚写的统计直接是错的），四次全是**文档在描述系统自己已经知道的事**。

但代码说不出四件事，且这四件的真相源本来就在仓库外：被排除的方案、约束的来源、失败的尝试、外部世界的事实。

**已确认的尺子：只写代码说不出来的东西。** 并且腐化风险与可重建性是**正相关**的——该删的恰好是既易腐化又易重建的那批，所以这刀几乎纯赚，不是权衡。

**已确认的第二条：沉淀应该是收割，不是另起一件事。** 用户很少沉淀不是懒，是沉淀要求在最累的时刻额外做一次人为判断；而 `ff` 能占 46% 且健康，因为它是工作的副产品。

## 5. 索引不值钱 → Project Spec 是结构性必腐的一层

我主张 spec 至少保留「索引和命名」，理由是不知道能力叫什么时读代码是指数搜索。

用户按实际体感否掉：「索引我觉得还好，我一般直接让 agent 去找花的时间也不会很多。」

**最终以此为准。** 顺出来一个结构性结论：

> Project Spec 描述**已经存在**的东西，天生是代码的第二份表述，所以结构性必腐；Epic Spec 描述**还不存在**的东西，代码里没有对应物，所以不腐。

推论：毕业规则要改。`close.md` 现在催 agent「把稳定结论的具体内容合并进 Project Spec」，等于在催它写最易腐的文字。应改为**从结论里筛出「代码里没有的那部分」**。

→ `byissue/decisions/004`

## 6. 用户抓到姿态漂移，以及三次同一个 bug

讨论中我多次以「要我现在就……吗」结尾，把 Talk 转成施工提案。用户点出来，并要求把它作为流程问题记下。

失败机制不是「急」：用户批准的自举是要动手的，**一次被授权的动作把整个会话的姿态从 Talk 悄悄翻成了执行**。而 `SKILL.md` 授权边界第一条「方向已确认就持续推进到完成，不要反复确认」又是通用强条，在 Talk 里有害。根本缺口是**姿态到底是会话级还是动作级，从没定义过**。

这时看出它和另外两件是同一件事：

| 应该发生的事 | 规则写了吗 | 触发了吗 |
|---|---|---|
| 沉淀（`close.md` 路由表） | 写了 | 否 |
| 姿态边界（`SKILL.md`） | 写了 | 否 |
| 讨论中拍板即时立碑（`talk.md`） | 写了 | 否 |
| 收尾提醒关闭（`do.md` 强制枚举） | 写了 | **是** |

**已确认的根因：** ByIssue 把「应该发生的事」写成了**描述性规则**（产物归属表），而唯一生效的那条写成了**强制枚举**（必须在收尾汇报中列出并显式询问）。

## 7. 和 grill-with-docs 对照：差别在语气

用户问这套东西是不是和 `mattpocock/skills` 的 `grill-with-docs` 很像。查证后：不只是像——ADR 的三条件门槛（难以逆转 / 离开语境会奇怪 / 真实取舍）和 ByIssue decisions 的三条件**一字不差**，提问轮次此前也已借用过（CHANGELOG 1.1.0 承认了后者，没承认前者）。

真正的差别不在内容，在语气：

- Matt 写祈使句，指挥会话中的行为：「Challenge against the glossary」「Update CONTEXT.md **right there**. Don't batch these up」「Surface it」。
- ByIssue 写描述句，规范产物归属：「拍板进 decisions/」「坑点 → notes」。

**归属表回答「东西该放哪」，但没有一句说「你现在必须做这个动作」。** 所以他的触发，我的不触发。

另外三条值得借：`CONTEXT.md` 是纯词汇表且明写「不要当 spec 用」；文件**懒创建**（有东西写才建，对照 ByIssue onboard 先建 8 个目录 + 2 个空骨架）；讨论中**主动与代码对照**而不只是冲突时仲裁。

一条不借：取消索引层——已在第 5 节按用户体感确认，结论殊途同归。

## 8. 提问必须带建议

用户补充：询问时要带建议，像 talk 的提问轮次那样——「我发现了 XXX，建议沉淀这些」，而不是「要不要沉淀」。

**已确认：** 这是**写作层通用契约**，不是 talk 的局部规矩。收尾沉淀、关闭提醒、姿态歧义时的选择，凡是向用户提问的地方都继承它。而且问题要有**事实答案**（「这是不是外部事实」）而不是**判断答案**（「这以后有用吗」），后者在人累的时候一定得到「算了」。

## 9. 编号：先量伤害，再选方案；A+B 里的 B 被实测否掉

不看碰撞率，看实际伤害。AGCopilot：裸编号引用 61 处、完整文件名引用 48 处；抽查碰撞号 `018`（三个文件共用）被引用 13 次，其中 11 次写了完整目录名，只有 2 次是裸的。**推算真正产生歧义的引用是个位数。**

同时我原本的论点塌了一半：我以为「取号要扫整棵树很贵」，但开工协议本来就要扫 `byissue/`，这笔钱已经付过。

三个选项：A 不动编号、把「引用必须给完整文件名」从只管 Epic Issue 扩展为通用强制（一行）；B 换日期前缀；C 加工具扫碰撞。

用户选 A+B。**B 随后被实测否掉：**

| 仓库 | 共享日期的事项占比 | 单日最多 |
|---|---|---|
| AGCopilot | 88% | 13 个 |
| byspace | 82% | 9 个 |
| pi-package-mono | 81% | 11 个 |

现状是 14% 的编号被共用，换日期后是 8 成以上的前缀被共用。B 想解决的观感问题会被放大六倍，而且日期把一个已知不可信的值（322 个里 3 个假日期）提升成了身份。

**最终以此为准：只做 A。** 并且把话说死：没有便宜的办法真正消除碰撞（根因是两个会话同时读到同一个 max），而碰撞的实际伤害只有个位数——正确答案是**接受碰撞，让它不疼**。

→ `byissue/decisions/005`

## 10. 真问题与出口

收束成一句：

> **ByIssue 的制度记忆里，会腐化的那部分（Project Spec 描述当前实现）不该写；不会腐化的那部分（词汇、被排除方案、外部事实）没有机制保证它被写下来。而根因是把「应该发生的事」写成了描述句而不是祈使句。**

**出口：** decisions `004`、`005`；issues `001`–`005`（沉淀收割契约 / Project Spec 瘦身 / 引用规则 / 姿态路由回归测试 / 姿态稳定性）。

**暂不纳入：** `decisions` 与 `-d-` 的处置（数据不足）；`done/` 残留清扫（用户判断没必要）；日期前缀方案（实测否决）；英文化（分发决策，非当前瓶颈）；存量 spec 批量重写（改为随 close 自然收敛）。
