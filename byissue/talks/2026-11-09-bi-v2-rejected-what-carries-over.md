## 1. 起点：用户想重新设计，不想只搬细节

2026-11-06，用户看到 cursor/plugins 里的 pstack，原话：「我其实也认可代码是唯一真相源这个事情的，然后我想的也是我们 bi 只是记录我们做过什么，和作为执行流程中的规范啥的」，「bi 的设计也是在旧时代定的……我现在想做的是拿着 bi 和 pstack 还有其他优秀的工作流，咱们来重新设计符合最新时代模型的新工作流，bi v2」。

pi 会话只给出了第一轮对照，之后接口持续 503，没能往下聊。

## 2. Codex 会话：用户的几条关键表态，和一次失控

用户在这里给出的几条，后来都没有被推翻：

- **宁可花 token，也不冒文档误导的风险。** 原话：「我更喜欢不节省那些 token……而不是承担文档腐化导致模型被误导的每一点可能性。因为重新调查的成本我觉得完全可以接受」。
- **参照的权重。** 原话：「superpower 在现在的时代已经是臃肿工作流的代表……pstack 作为最新比较火的现代工作流，我觉得参考程度可以加高一点」。
- **为什么弃用 OpenSpec。** 原话：「spec 容易腐化，遇到大的任务工作流效果很差……如果是大任务，（我懒得手动拆）就会导致会话压缩几轮，模型就一定跑偏，一定是会忘记要做什么，或者漏细节的」。
- **形态。** 原话：「这个需要保持和 bi 一样的定位，纯 Skill，不需要适配，任何支持 skill 的都应该能用」。

那个 agent 也提出过一个后来被用户采纳的问题：记录被下一个 agent 采用，凭的是什么？它举了三个例子，用户原话（需求依据）、一次观察（调查线索，需要复核）、可以重跑的脚本（直接重跑），说明这三样应该区别对待。

失控的经过：研究还没形成共同理解，它就接连提出「拍平成一项工作」等方案，问题越提越多，没有一个谈完。用户叫停，原话：「我完全不知道你在干嘛……你应该先帮我理清楚 pstack 和 bi 这两个东西」。

## 3. Claude 会话：两张地图，和用户的四点校正

接手的会话把两者分开讲清楚。bi 管项目的目标、认知和变化怎样跨会话接续；pstack 管 agent 接到目标后怎样调查、设计、分工、验证和交付。它还指出 pstack 也没有消灭文档腐化：它的验证地图（verification feature map）同样要持续维护，修法是逐个功能对照源码、实际运行，而不是相信文档本身。

用户的四点校正（原话节选）：

1. 「recall 应该是我们说的那个仓库的超集吧……如果这个你通过本环境可以获得的信息获取到了，比如 git 历史你能拿到的信息，那就没必要再写一份文档」，「我想要的是反正换个 agent 来，信息获取到的都是差不多的」。
2. 大任务的关键是拆分：「比如说一个重写前端的任务，因为范围很大，他可能写在 task 里的就只有一点重新 xxx 功能……而导致实现偏移」。
3. 「map 要维护是应该的，我说的是成百上千个 spec 文档，那才是最容易腐化误导的」。
4. 「pstack 确实可以完全上位当成基底」。

随后它把 pstack fork 进 `v2` 分支、开始往单 Skill 的形态迁移。用户中途叫停：先去实际用 pstack-claude，再决定改造谁。之后清理回 `main`，删掉了 `v2` 和其他已合并的分支。

## 4. 2026-11-09：否决 v2

用户原话：「我自己实际使用之后觉得，pstack 并没有实现我想要的效果，所以我这边的结论是否定做 v2 版本。继续只吸收优化我们的。但是之前讨论过程中的一些内容我觉得仍然有意义」。

**已确认：** 不 fork pstack，不做 v2。pstack 里好用的做法按条吸收，第一批见 `byissue/talks/2026-11-09-what-to-absorb-from-pstack.md`。

## 6. 出口

**已执行（1.12.0）：** 沉淀直接落盘；收尾、关闭、提交、推送一句触发固定顺序；记录分三种用途、读观察先复核；吸收 pstack 的 deslop 与 no-comments（`references/economy.md`「交付前清理自己的 diff」）和 unslop（改写成中文的 `references/writing.md`）。

- 「做完了，收尾吧」：全程没有提问。先写 note 和 spec，再修引用、改名，然后跑脚本，最后只提交一次，没有推送。note 的「依据」里分开写了用户转达的内容、带版本的观察和复核方法；Windows 上的 GBK 解码标成了推断。
- 快改价格格式：发现 README 给的测试命令一个测试都不跑，换了命令重跑。spec 新约束引了用户原话，并把「长期有效」是自己推断的这一点列进了「需要你看的」。没有提交。
- 快改并「直接提交」，夹具里另有一个等待验收的无关 `-o-` issue：那个 issue 保持开着，commit 里只有 README 和 ff。
- 讨论姿态里说「收尾」：给出口草案和一个带推荐的问题，没写任何文件，没有提交。它在临时目录里跑了探针来验证 CSV 的行为。

还没有行为证据的两条：无痕迹例外下说「提交」；「交付前清理自己的 diff」对真实 AI 痕迹有没有效果，四个夹具的改动都太小，测不出来。
