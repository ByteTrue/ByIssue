## 候选汇总

### 候选一：夹具搭完先自证前提（对应第 124 行 fake-pi.test.mjs「装置自己会喊」，部分已有）

**做什么。** pstack 每个测试装置在跑被测对象之前先证自己造对了场景：`fake-pi` 认不出步骤就跑 `exit 64`（fake-pi.mjs:21-24），`fake-pi.test.mjs` 逐条证明这个喊声真的会响；worktree 那条更直接——夹具先断言「我确实复现了隐藏产物」，`assert.equal(git(wt.path, "status", "--porcelain", "--ignored"), "", "fixture must reproduce the hidden output")`（worktree-status-config.test.mjs:59）。

**挡什么。** 挡 ByIssue 评测里最贵的一类浪费：**夹具没造出要测的东西，观测作废，而结果看起来像一次有效评测**。已真发生过两次，都是成批的跑白费：
- `tools/posture-scenarios.md:14`「实测三种失败形态，都是 fixture 缺目标物、不是路由错，观测作废」——「把这个 epic 关了吧」撞上空 `epics/`、「顺手改一下这个 README 里的错别字」而仓库里没有错别字（16 轮烧在通读两个 README 上）。
- `byissue/notes/2026-11-09-posture-table-on-deepseek.md`「场景 30 原夹具的 `old/` 只有一个 21 行的脚本，DeepSeek 会合理地判断「一次对照就能确认」，不走 large，所以那个夹具判不出这条规则」；同文末尾「夹具源码太小时，模型读一遍代码就能定位，不会进 `debug.md`「升级」…要测升级路径上的规则，夹具得让读代码定位不了」。

**已有多少。** checker 侧已有完全同形的装置：`tools/check-skill-repository-selftest.py:2-5`「Prove every check … can actually fail … A check that cannot go red here guards nothing」，19 个坏夹具逐个必须报错。缺的只是把这条纪律搬到 `tools/fixtures/` 的三个夹具生成器（`posture_table.py`、`close-reference-repair.sh`、`state-letter-probe.sh`）。

**零依赖做法。** 全部标准库 Python + 已有 shell，不加依赖：
- `tools/fixtures/posture_table.py` 每建完一个夹具，立刻跑该场景自己的前提断言，失败就非零退出并指名场景号。落成几条具体断言即可：场景 26 的夹具里 `grep -rn` 真的命中九类形态各≥1 处、`notes/n.md` 真的引用了待改路径；状态字母五臂的目录名真的是 `-w-`/`-o-`/`-x-` 且 `w-violation` 臂里真有 `-o-` 子 issue；场景 19/20 的仓库里「没有」不该有的 issue 文件；场景 28 的 README 里那一行命令真的拼错。
- `close-reference-repair.sh` 与 `state-letter-probe.sh` 末尾各加一段 `set -e` 下的自检（建完立刻 grep 一遍，命中数为 0 就 `exit 1`）。
- 断言文案写明「fixture must reproduce …」，让下一次看见红的人知道红的是夹具不是被测对象。

**落点。** `tools/fixtures/posture_table.py` 为主，两个 `.sh` 各加尾段；`tools/posture-scenarios.md` 的「怎么跑」加一句「搭完先跑夹具自检，红了不要开跑」。

**成本。** 半天以内，约 40–70 行 Python、两个 shell 尾段。收益是每次评测少整批重跑；风险很低（只加断言，不动夹具内容）。

### 候选二：计分要能从产物判，并且「没跑 / 跑挂」不能冒充「通过」（对应第 129 行 live.test.mjs，部分已有）

**做什么。** pstack 的 live 套件两头都硬：一头是断言落在可观测产物上（进程真死 `expect(pidAlive(sleeper.pid)).toBe(false)`、文件内容真是 `BRAVO`、worktree 真被删），另一头是「没跑」永远可见——`const LIVE = process.env.PSTACK_PI_LIVE === "1"`（live.test.mjs:21）配 `describe.skip`，而一旦声明「这次必须跑」，缺输入就抛错而不是跳过（`catalog.test.mjs:31-36`「so a catalog that moved fails there instead of skipping」/ `if (!catalog) throw new Error(...)`）。

**挡什么。** 挡「一次失败的检查看起来和一次干净的检查一模一样」。ByIssue 今天正是这个形状，而且已经踩过：
- `tools/fixtures/posture_judge.py:77` 打出 `routing: 3/5 clean` 之后 `main()` 直接返回——**脚本永远退出 0**，谁也没法把它挂进任何流程；`posture_judge.py:9-11` 自己写明「Behavior assertions (the plan's check column) still need a look at the fixture; this script only prints its git state」，即行为那一半是人工。
- 已发生的同类失败：`byissue/issues/009-x-ff-tidy-tools-scripts.md` 记 checker 的 `LINK_RE`「既不校验也不报错，是个静默漏检」；`tools/prompt-review.md:9`「一份**中途截断**的报告看起来与「查完了，很干净」一模一样」；`tools/retro-failure-modes.md:81`「8 条里有 5 条是「观测工具污染了观测对象」…它产出的是**看起来有效的错误结论**」。
- 更贵的版本是自述冒充产物：`tools/prompt-review.md:18`「记录里写「已改为 X」而文件里不是 X，是同一类错误里最贵的一种」；`CHANGELOG.md:54`（1.13.0）记的真实事故「the frontend rewrite logged at least seven "漏了" including a step reported done with `/new` still a placeholder」。

**已有多少。** 判据侧已有且写得很清楚（`tools/posture-scenarios.md:79`「**判据是夹具文件的最终状态，不是子 agent 的自述**」、`:24`「判据是调用序列，不是它自己的说法」）；缺的是让脚本执行它，以及让「没跑」与「通过」分开。

**零依赖做法。**
1. `posture_judge.py` 末尾 `sys.exit(1 if bad or missing else 0)`；`no session log` 记为「未跑」并在汇总里单列一行，不算 clean。
2. `posture_table.py` 现在给每条 plan 一个 `check` 文本（给人看）。改成结构化的一小组机械断言：`{"files_exist": [...], "files_absent": [...], "contains": {"<rel>": ["<substr>", ...]}, "git": {"commits": 1, "dirty": 0}}`，`posture_judge.py` 逐条判并计入 `bad`。可机器判的挑最关键的几条即可（场景 26 的改名与引用归零、场景 19/31 的不建 issue + 落 `ff`、场景 28 的无关 `-o-` 未动）。判不了的仍留给人工，但要在输出里标 `manual`，不许混进 clean 计数。
3. 两条模式：默认「只算路由」，`--require` 时任何一行未跑或人工项未标过就当失败。对应 pstack 的 `PSTACK_PI_REQUIRE_*`。

**落点。** `tools/fixtures/posture_judge.py`（退出码、结构化断言、`manual` 标记）、`tools/fixtures/posture_table.py`（plan 的 `check` 字段结构化）、`tools/posture-scenarios.md` 的「怎么跑」与 `byissue/spec/index.md:52`「动过姿态表或必读文件后跑姿态评测 | 无」这一行（跑完能留一个非零/零的退出码，强制者就从「无」变成「脚本」）。

**成本。** 一天左右。风险在把断言写得太死（夹具措辞一变就红）——所以只挑「契约必须成立」的那几条，不抄整个场景描述。

### 候选三：给上游逐字节镜像上钉（对应第 134 行 slash.test.mjs）

**做什么。** pstack 把 pi 不导出的实现抄了一份，然后拿真上游逐输入对拍：`expect([line, parseCommandArgs(line)]).toEqual([line, pi.parseCommandArgs(line)])`（slash.test.mjs:25），一句注释写明目的「so a pi release that changes them fails instead of drifting」（:2）。

**挡什么。** 挡「勿手改」这类规则在下一次顺手清理里被违反而无人发现。ByIssue 有两条这样的镜像：`byissue/spec/index.md:18`「**正文为上游 `mattpocock/skills` `grilling` 的逐字节镜像（ff 015）：勿手改，同步上游时整文件替换。**」，`byissue/spec/index.md:19` domain-modeling 的「**读侧是上游的句级镜像：勿按项目口味改写**」。而 `CHANGELOG.md` 1.13.2 一次就「36 lines across 16 files deleted or rewritten」，同类批量清理随时会扫到这两个文件。

**拿不准的部分。** 我没找到 ByIssue 历史上真发生过一次「镜像被手改」的记录：`git log -- skills/bi/references/grilling.md` 只有建档那一条（bc6821b），`domain-modeling.md` 另有一次 1.9.0 的改动（7a5b1d8）但记录没说是改了读侧。缺的证据是：一次真实的镜像漂移事故，或 `decisions/` 里对「镜像是否算同一归属」的裁决。这一条是预防性的，不是补漏。

**与 pstack 的差别（要写明）。** pstack 比的是**真上游**（已装的 pi 就在磁盘上）；ByIssue 零依赖、不上网、上游不在仓库里，所以只能钉**哈希**：记住镜像建立时的 sha256，之后任何字节改动都要连哈希一起改。它挡手改，**不挡上游自己改版**——后者只能等下一次人工同步。

**零依赖做法。** `tools/check-skill-repository.py` 加一张常量表 `MIRRORS = {"references/grilling.md": "<sha256>", "references/domain-modeling.md#读侧": "…"}`（domain-modeling 只有读侧是镜像，哈希整文件会把可改的写侧也钉住——这一条要么先拆文件，要么只钉 grilling，等用户定）；`tools/check-skill-repository-selftest.py` 加两个坏夹具（改一个字节必须报 `mirror drifted: references/grilling.md`）。报错文案要写清「改了镜像就要同时改哈希，并在 CHANGELOG 里写明是同步上游还是有意偏离」。

**落点。** `tools/check-skill-repository.py`（一条 `check_mirrors`）、`tools/check-skill-repository-selftest.py`（两个 case）、`byissue/spec/index.md:18` 那两句加一句「哈希由 checker 钉住」。

**成本。** 半小时到一小时（domain-modeling 的读侧边界另算）。风险：如果用户希望 grilling 允许项目化改写，这条就应当判不吸收——它保的是「逐字节」这个承诺本身。
