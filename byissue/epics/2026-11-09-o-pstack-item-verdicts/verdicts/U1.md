## 候选汇总

### playbook `perf-issue`（候选）

pstack 原句：「**You own the measurement story. Plan, review, verify the numbers.** Tie every fix to a measurement, don't read source instead of measuring.」「Capture a baseline trace」「Parse and compare the artifacts (JSON to sqlite, diff). "Inconclusive" or wrong-surface is not a pass.」

补的 bi 缺口：bi 收了「性能回退」这个场景（`complain.md:76`「不符合预期、行为跑偏、debug、日志/截图/测试失败、性能回退。」），但没有「改前先取基线、改后用同一基准对照」这个动作。`quality.md:52` 只把「基准」列为可用证据之一，没规定性能类改动必须给出 before→after 两个数。

建议落点：`skills/bi/references/quality.md`「工程手段与质量特征」之后加一小段（性能效率那一行只有「响应、吞吐、资源和容量是否满足明确条件」）。写法：性能回退类改动先在同一基准上取 before，改后用同一命令取 after，两个数都贴出来；只取到一处、或换了场景比的，按 `SKILL.md:18` 算「无法判定」。

为什么是真实默认：模型被说「有点慢」会直接读代码挑一个看起来热的地方，改完自述「应该快了不少」；这正是 pstack 那句 don't read source instead of measuring 挡的行为，也是 talk 第 6 节里尚未取证的那批默认之一。

### playbook `runtime-forensics`（候选）

pstack 原句：「**You own the diagnosis. Instrument the live process, don't theorize from source.** The deliverable is a cited diagnosis, not a fix.」「Reduce the artifact to the smoking gun: the function on the hot path, the retainer chain from the leaked object to a GC root」「Map the finding back to source: file, symbol, the line that allocates or schedules.」

补的 bi 缺口：`debug.md:22` 的证据全部是「用户步骤、堆栈、日志、截图、挂掉的测试」；升级路径第 2 步要求「可证伪假设……若真，应看到 Y」，但从没说 Y 要自己去采。泄漏、空转、偶发卡顿这类症状，bi 现在只有「从源码推」一条路。

建议落点：`skills/bi/references/debug.md`「升级：快路径不够时再用」的第 2 步旁边加一句：这类症状先采一份真实 artifact（profile、heap snapshot、trace 或一段计时日志），把读数收敛到一条签名，再回源码定位到具体分配/调度点；只有源码推断时按 `SKILL.md:18` 标「推断」，不叫诊断。只能加在升级路径——`complain.md:21`「不要一上来就搭复现脚本或失败测试」是快路径的刻意设计，不能被这条推翻。

为什么是真实默认：模型面对「内存一直涨」几乎总是从源码讲一个可能的原因，而不是去要一份 heap snapshot；它也没有「没有源码映射的帧不算诊断」这个停止条件。

### playbook `trace-forensics`（候选，与上一条同一落点）

pstack 原句：「Distinct from **Runtime forensics**, which instruments the live process. Here the capture already exists. The artifact is a fixed dataset, read it, don't re-run it.」「Dump the trace or heap snapshot into sqlite, one row per sample, frame, or node. Reach the queryable shape before you read.」「A frame with no source mapping is not yet a diagnosis.」

补的 bi 缺口：用户直接把一份 `.cpuprofile`／heapsnapshot／spindump 丢过来时，bi 没有任何一步说「先转成可查询的形状再读」，也没有「不要为了看它而重跑」的约束。

建议落点：与 `runtime-forensics` 合成 `skills/bi/references/debug.md` 同一小节的两句——有 capture 就直接读（先用 stdlib Python/sqlite 摊成一行一样本的表，不重跑、不用 Node 工具），没有 capture 才去采。分两节写会重复同一件事。

为什么是真实默认：模型拿到大 JSON 会直接读前几百行、或 grep 几个词然后猜；重跑一次去「看得更清楚」也是常见动作，而对固定产物来说是白花时间且改了条件。

### playbook `visual-parity`（候选）

pstack 原句：「Establish the baseline first, before any migration: a visual regression harness that screenshots the current component across its states, plus the target when matching two implementations. No baseline, no parity claim. A blocking prerequisite, not a follow-up.」「Anti-shortcut clauses, stated and held: no harness modifications, no baseline tampering, no component restructuring to make a diff pass.」「Verify each component against its baseline via image diff on the matching surface. A nonzero diff is a fail.」

补的 bi 缺口：`ui-spec.md:61` 只说「线框图能澄清目标，但不是达成目标的验证证据」，`do.md:69` 只要求「截图或 DOM 边界检查须覆盖该动态态」。两处都停在「看一眼」，缺三件事：迁移前先建基线、按组件逐一对图 diff、diff 非零即失败且不许改基线让它变绿。

建议落点：`skills/bi/references/ui-spec.md` 新增一小节「视觉等价怎么验证」，放在「一张 UI 规格需要说明什么」之后（那一节末尾正好接着讲动态状态的空间契约）。内容只要三句：换样式系统或对齐两套实现前，先给当前实现按状态截一组基线；逐组件改、逐组件对图 diff；diff 非零就是没做到，基线看着不对要停下来问，不能改基线。

为什么是真实默认：改 CSS 的 agent 会说「视觉上一致」然后合并；被图 diff 拦住时，最容易的动作是更新基线快照让测试变绿——pstack 那句 no baseline tampering 挡的就是这个。

### playbook `prototype` 缺的那一块（候选）

pstack 原句：「Build throwaway in an isolated scratch dir, separate from production source. For a visual decision, vanilla HTML/CSS/JS or the lightest stack that renders the idea」「When comparing alternatives, build them behind one switcher (buttons or a keypress), each variant labeled.」

补的 bi 缺口：`SKILL.md:24` 已经要求「先用最小探针或一次性原型（跑完即删）跑出结果」，但没说搭在哪，也没说多方案怎么摆。默认结果是原型文件落进源码树。

建议落点：`SKILL.md:24` 那一句后面加半句「搭在仓库外的临时目录」，成本是一个从句；多方案同屏切换只在真要比两个方向时才需要，可以并进 `references/design.md`「验证策略」，不进 SKILL.md。

为什么是真实默认：要验证一个交互分叉，agent 最省事的做法是在当前仓库加一个 demo 文件或临时路由，跑完留在 diff 里，要么被 economy「交付前清理自己的 diff」事后删掉，要么漏删。

### playbook `pause-safely` 缺的那一块（候选）

pstack 原句：「Stop at a safe boundary. Finish the current atomic step or back out of it. Start nothing new, and cancel any nested subagents.」「Take no irreversible action to pause. No PR and no push unless you already had one out.」

补的 bi 缺口：bi 有接续点的**写法**（`do.md:83`、`large.md:52`），但没有收工**那一刻**的动作约束：停在原子步骤边界、不启动新步骤、不借收工做不可逆动作。pstack 还有一条 bi 明确不接的（`commit` 一个 `wip:`），`SKILL.md:238` 已经不自动 commit，那半条不进来。

建议落点：`skills/bi/references/do.md` 产物契约里「接续点」那一条之前加一句（同一节，讲「没做完就收工时」的动作与写法）；`large.md:52` 已经链接到接续点语义，不必重复。

为什么是真实默认：上下文将满或用户要走时，agent 会抓紧再开一个新步骤，或者顺手把工作区提交/推送掉；这两件在收工时刻的代价最高。

### playbook `autonomous-run` 缺的那一块（候选）

pstack 原句：「State the exit condition as a checkable predicate before the first iteration (tests green, repro fixed, all N PRs merged, pixel-diff zero).」「Stop when the predicate is met. A plateau is not a stop, so keep going and pivot your approach to push past it… and never relax the predicate to declare victory.」

补的 bi 缺口：「持续推进不停」已有（`SKILL.md:67`）。缺的是开工前把「做完」写成一个可检查判据。bi 只有大任务路径有对应物（`large.md` 第 2 步把已定方案写进 Epic spec，关闭条件在 spec 里），用户说「跑完为止」的单任务长跑没有这一步，完成定义要到汇报时才成形。

建议落点：`skills/bi/references/do.md`「实现与验证」之前的锁定段加一句：这种长跑开工前先用一句可检查的话写下「做完是什么样」（哪条测试绿、哪个复现不再出现），中途不得改写它来宣称完成；做不到就按 `SKILL.md:18` 报「未通过/无法判定」。不要动 `SKILL.md:67`，那条讲的是途中确认节奏，不是完成判据。

为什么是真实默认：这是「移动球门」——每轮把目标重述成已经做到的事，然后在汇报里宣布完成；也在 talk 第 6 节尚未取证的那批默认里。

### playbook `hillclimb` 缺的那一块（不吸收）

pstack 原句：「fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run」「Loop, one hypothesis per iteration… One commit per accepted fix… Log the row either way, kept or reverted.」

不吸收的理由：缺的那半块是「agent 自己定指标、自己定阈值、每轮一次 commit、用 `decision.tsv` 记每轮」的持续优化循环。它与 bi 两条现有契约冲突：`quality.md:41`「指标阈值、成本显著增加、兼容策略和质量目标冲突等产品取舍必须交给用户」；`SKILL.md:238`「**默认不做三件事：不自动 commit、不自动 push / 发布、不自动关闭常规 Issue。**」。轨迹的去向在 bi 里是 issue 的执行记录与 `byissue/`，不是 `decision.tsv`。其中唯一可迁移的「同一基准前后测量」已经并入上面 `perf-issue` 那条候选。
