## 候选汇总

### 1. skill `benchmark-checklist`（候选项本体）

- pstack 原句：`benchmark-checklist/SKILL.md:8`「Use this when you produce a performance number... Answer each question with evidence from a run, not a guess about the code.」`;20`「Why not double? Name the limiter.」`;24`「Run each side at least 5 times, alternating (A, B, A, B, and so on)...A gap smaller than the run-to-run variation is no measurable difference.」`;26`「Confirm the work ran inside the timed region」`;32`「Call the verdict inconclusive when you claim a difference but cannot name the limiter」。
- bi 的缺口：`SKILL.md:18` 只要求把结论标成实测或推断，`writing.md:9` 只要求把「性能好了很多」换成具体数字，`quality.md:14` 只把性能效率列为质量特征——三处都在管「怎么说」，没有一处管「这个数是不是量到了它声称的东西」。
- 建议落点：`quality.md` 新增一节「性能数字的验收」，放在「工程手段与质量特征」与「应用边界」之间：先写下准备声称的那句话；命名 limiter，否则判无法判定；两边按生产配置各跑一遍，一边跑默认值就只能说「比较的是配置」；至少 5 次交替，报中位数与范围，差距小于轮间波动就是无可测差异；数失败与非成功响应；确认计时区间里工作真的发生了。同时把「应用边界」里「也不提供…完整测量方法」收窄成只说 ISO 合规与认证，否则两句互相打脸。在 `SKILL.md:18` 加一句指过去：「性能数字按 quality.md「性能数字的验收」过一遍再报。」
- 为什么是模型的真实默认：给它一个 before/after 的单次运行，它就会写成「快了 30%」；它不会去找限速环节，不会交替跑，不会怀疑加速来自缓存命中，也不会检查被优化的那段代码在计时区间里是否真的被执行——这些正是 pstack 那七问逐条在挡的。

### 2. skill `create-verification-skill`（候选项本体）

- pstack 原句：`create-verification-skill/SKILL.md:16`「Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence.」`;26`「can two instances run side by side (ports, data dirs, profiles)? If not, say so...refusing to double-drive a shared instance beats corrupting the user's session.」`;37`「exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects...alongside what's visible」`;47`「Run its own instructions end to end once...A generated skill that was never executed is a draft, not a deliverable.」
- bi 的缺口：`do.md:28`「非平凡逻辑至少一个会在行为损坏时失败的最小可运行检查」、`economy.md:74`「优先复用现有测试入口和用户可观察接口」、`maketools.md:13`「跑通后必写 notes/」都假定「已经有一个能驱动真实东西的入口」或「有人带路」。项目没有这个入口时，bi 没有一句让 agent 去把它造出来并跑通。
- 建议落点：`maketools.md`「产物契约」之后新增一节「项目没有可脚本化验证入口时」：从仓库（README、package scripts、Makefile、已有 e2e、端口与 env）问出四件事——怎么启动到可用、怎么用程序驱动真实用户路径、抓什么证据、怎么隔离（并发实例、临时数据目录、不驱动不是本次启动的实例）；写进 `byissue/tools/` 或 `notes/`，并按它跑通一次再算完成；驱动不通就说「无法判定」，不许拿单测或只编译通过代替。落点留在 `byissue/` 内，不生成 `.claude/skills/verify/`，守 `SKILL.md:201`。从 `do.md:28`、`fast.md:47` 各链一句过去。
- 为什么是模型的真实默认：模型默认把「单测绿了」当成「行为对了」，去 curl 一个 test-only 端点或内部 setter 就宣布验证通过；它很少先确认「这个仓库到底怎么把真东西跑起来」，更不会为一次观察专门写驱动、隔离实例、留证据，也几乎不会在交活前按自己写的步骤走一遍。

### 3. skill `architect` 缺的那一块（两条设计红旗）

- pstack 原句：`architect/references/design-red-flags.md:19`「Information leakage makes multiple modules depend on the same internal decision. A representation, policy, or protocol detail appears in more than one place, so changing it requires coordinated edits.」`;21`「Public re-exports of transport or wire types are leakage. Parse external data into domain types behind the interface.」`;25`「Temporal decomposition organizes modules by execution order instead of the knowledge they own. Separate load, validate, transform, and save stages often repeat one representation and its invariants across several boundaries.」
- bi 的缺口：`code-design.md:60`「让从一个文件看起来对的改动，对全仓也对」只列了四种形状（同一件事两种做法、手工同步清单、多写入方、可导入内部），没有「同一个表示/协议细节被多个模块依赖」和「按执行阶段而不是知识归属切模块」这两条；`code-design.md:88` 只管「同一条规则散落在前端、API、数据库和测试里各写一遍」，管不到「DB 行类型/传输类型直接出现在公开接口上」。
- 建议落点：`code-design.md:60` 那张清单加两条：「**表示泄漏**：同一个内部表示（存储行、线上协议、框架对象）被两个以上模块直接依赖，改它要一起改。在边界处解析成领域类型，内部只认领域类型。」「**按时序切模块**：模块边界跟着 load/validate/transform/save 的阶段走，同一个不变量在几段里各写一遍。按知识归属切，同一决定的代码放一处。」
- 为什么是模型的真实默认：最短路是把数据库行或接口响应原样往上传，因为那样能编译、少写一层转换；模块也天然按「先读、再校验、再转换、再存」的执行顺序分文件，因为那是它写代码的顺序。

### 4. skill `correct` 缺的那一块（新检查要先红一次）

- pstack 原句：`correct/SKILL.md:25`「Prove each new check fails on a real past mistake. Run the same command locally and in CI.」
- bi 的缺口：`SKILL.md:203` 只说「首选落成一条会在复发时失败的检查（测试、类型约束、lint 规则或脚本）」，没有要求在落盘前拿真实旧错或故意做坏的副本看它红一次。`debug.md:51`「补上后先跑一次，确认它失败的内容正是你预测的那个偏差」只管 bug 的失败测试，管不到新加的 lint 规则、类型约束和脚本。
- 建议落点：`SKILL.md:203` 那句后面加半句：「落盘前先拿一条真实旧错（或故意做坏的副本）看它红一次，没红过的检查不算挡住。」只改 `SKILL.md`，不在 reference 重述——它在上下文里，改一处就够。
- 为什么是模型的真实默认：模型很愿意加一条永远为真的测试或一条从没触发过的 lint，然后宣称「以后不会再犯」；它不会主动构造一次违例去证明检查有效。本 Epic 自己的 spec 里「checker 自己不漏检」也要靠自测，是同一个坑。

### 5. skill `ketchup` 缺的那一块（待定事项要自带判断材料）

- pstack 原句：`ketchup/SKILL.md:8`「Then lay out every call waiting on them so they can make it from your reply alone.」`;18`「For each item, collect its link, what it changes for users, the evidence behind your pick, its risk, and your pick.」`;22`「A link can add depth, but the reply alone must be enough to decide.」
- bi 的缺口：`SKILL.md:18` 要求把推断与无法判定的项列进「需要你看的」，`SKILL.md:22` 要求「每条附**推荐答案和一句理由**」，`SKILL.md:24` 要求把待裁决清单「列出候选并标明建议留哪些、不建议哪些」——都给到建议这一层，没要求给「这条改动对用户意味着什么、建议背后的证据是什么、风险是什么」。用户往往还得追问一轮才能定。
- 建议落点：`SKILL.md:24` 那段「需要用户裁决的清单」后面补一句格式要求：每条待定事项自带链接或路径、它改变了用户的什么、支撑建议的那条证据（命令与输出、日志、截图位置）、风险、以及推荐；只凭这条回复就能定，缺哪一项就说「不知道」，不拿一句「你看要不要」代替。
- 为什么是模型的真实默认：模型汇报完就停，或抛一个裸问题「需要我继续吗」；它默认「用户知道上下文」，不肯把影响、证据和风险压缩成一段可决定的话，于是每次都换来一轮澄清。
