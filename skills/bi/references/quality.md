# 原则：质量特征与承诺

软件质量要在当前变化的目标、设计和证明里出现。ByIssue 使用 ISO/IEC 25010:2023 的产品质量模型作为共同语言，只有会改变方案、实现或验收的质量目标才成为本次工作的约束。

## 九项产品质量特征

| 特性 | 当前变化需要关注什么 | 子特性提示 |
|---|---|---|
| 功能适宜性（Functional suitability） | 功能是否覆盖目标、结果是否正确、步骤是否适合任务 | 功能完整性、功能正确性、功能适当性 |
| 性能效率（Performance efficiency） | 响应、吞吐、资源和容量是否满足明确条件 | 时间特性、资源利用、容量 |
| 兼容性（Compatibility） | 是否能与其他产品共存并正确交换、使用信息 | 共存性、互操作性 |
| 交互能力（Interaction capability） | 指定用户能否识别、学习、操作并获得必要帮助 | 易识别、易学、易操作、用户差错防御、包容性、用户辅助、自描述性 |
| 可靠性（Reliability） | 正常和故障条件下能否持续工作、容错并恢复 | 无故障性、可用性、容错性、可恢复性 |
| 信息安全性（Security） | 信息和操作是否抵御未授权访问、篡改与攻击 | 保密性、完整性、抗抵赖性、可核查性、真实性、抗攻击性 |
| 可维护性（Maintainability） | 维护者能否理解、修改、复用和测试 | 模块化、可复用性、可分析性、可修改性、可测试性 |
| 灵活性（Flexibility） | 产品能否适应需求、负载、情境和运行环境变化 | 适应性、可伸缩性、易安装性、可替换性 |
| 安全性（Safety） | 是否能避免危及生命、健康、财产或环境的状态 | 运行约束、风险识别、失效安全、危险告警、安全集成 |

信息安全性面向恶意行为、越权和信息保护。安全性面向人身、财产与环境危害。需要同时提及时并列写全名。模型来源见 [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)。

## 选中即承诺

先用九项特征扫描当前变化可能伤到什么，再只选择会改变判断的少数项目。不要为了凑分类填写“满足”或“不适用”。

每个选中的质量目标写清：

- 特性，必要时收窄到子特性。
- 在什么条件下，系统应当达到什么可观察结果。
- 目标来自用户确认、`memory/` 中的长期约束，还是本次风险判断。
- 用什么证据判断它是否达到。

“保证可靠性”“注意性能”不是质量目标。可执行的表达是：“相同扣款请求重复提交时只产生一笔交易；用幂等集成检查验证”。

## 质量目标如何进入 work

`work/{slug}/index.md` 保存本次目标、边界和行为证明。质量目标要落到行为证明表的“应观察到”或“证据”列，并在真实入口上验证。测试、静态检查、评审、基准、故障演练和手动路径都可以成为证据，强度与失败代价匹配。

`vision/` 里的质量方向是长期目标。稳定的质量约束和用户取舍写入 `memory/`，当前变化只引用它们并写本次的可观察结果。没有长期约束的临时风险留在 work。

## 必须保留的工程护栏

质量目标之外，以下内容始终属于完整变化的一部分：信任边界的输入校验、权限与信息安全性控制，防止数据丢失或不可恢复副作用的错误处理，相关时的安全性约束，可访问性基础，危险操作护栏，以及与失败代价相称的验证证据。

可测试性是可维护性的子特性。可观测性可以支撑可靠性、信息安全性和验证证据，但它本身不是第十项产品质量特征。图示和原型可以澄清交互目标，不能替代可运行路径或检查结果。

质量规则不提供 ISO 合规或认证结论，也不替代领域法规、功能安全分析和组织级质量制度。
