# 原则：UI 可视化规格

UI 需求中的区域位置、信息层级、动作关系和状态变化，常常不能靠一句“增加设置页”说明。可版本化的简图把这些关系放进 `vision/` 或当前 work。

## 什么时候必须画

UI 变化满足以下任一条件时，提供可视化规格：

- 区域位置、分栏、分组、层级或控件共置关系会影响需求理解。
- 页面、面板、弹窗、导航或多步骤流程之间存在关系。
- 关键状态会改变结构或可用动作，例如加载、空、错误、禁用、未登录、执行中或二次确认。
- 响应式尺寸会改变布局结构，而不只是等比例缩小。
- 当前界面与目标界面的差异仅靠段落难以判断。

纯后端能力、简单文案、颜色或设计 token 调整，以及不涉及空间和状态歧义的单一控件变化，不需要为了完整而生成空线框图。

## 选择合适的图

默认使用简短 ASCII 或 Unicode 线框图表达区域、相对位置、层级、主要控件和可见状态。只保留影响理解的节点，不提前写组件名、CSS 属性或实现层级。

页面跳转、操作流程、状态迁移和多分支反馈更适合 Mermaid。截图、设计稿和可运行原型可以表达视觉证据，但不能成为唯一规格。

## 一张 UI 规格需要说明什么

图和相邻文字共同回答：

- 谁在什么场景进入这个界面，要完成什么任务。
- 这是当前界面、目标界面还是讨论中的示意。
- 主要区域、信息层级、控件共置和导航方向是什么。
- 哪些动作改变什么状态，用户看到什么反馈。
- 哪些位置、层级、可见性或动作关系必须保持。
- 哪些文字、尺寸、顺序或视觉细节仍可由后续设计决定。

出现 hover、focus、展开、popover、悬挂按钮或其他越出静态盒子的状态时，标出它相对宿主、相邻内容和裁切容器的边界。可见面与命中区可以不同大，但不得遮挡正文、意外裁切或造成布局跳动。

涉及交互能力时，用 [quality](quality.md) 判断易操作、用户差错防御、包容性和自描述性是否需要成为质量目标。线框图能澄清目标，不能证明目标已经达成。

## 真相放在哪里

`vision/` 保存跨多个变化的目标体验、用户旅程、页面关系和候选方向。当前稳定的界面关系和长期交互原则写入 `memory/`。本次变化只在 `work/{slug}/index.md` 里画相关局部和状态，并在行为证明表中验证真实入口。

图示状态必须明确是当前、目标、候选还是示意。不要把当前和目标混在一张没有标注的图里。图与文字冲突时，先核对用户最新确认和真实证据，再同步修正。
