# 大任务：台账、单元与重读

用户交来的任务做没做全，靠一次观察确认不了时用这份，判据见 `SKILL.md`「选择管理强度」。

## 背景

大任务常见的失败有两种。第一种是漏项：单元清单出自 agent 的理解，每个单元做完只对照自己那份清单，没进清单的东西从头到尾没人做，最后却报「做完了」。第二种是方案和约束丢了：谈好的方案只留在对话里，几轮压缩之后 agent 忘了，自己另起一套，或者违反了说好要守住的约束。

两种失败的解法相同：磁盘上有一份全量的东西，并在固定时点重读它。全量清单就是台账，已定的方案和约束写进 Epic spec。

## 开工前

下面五步做完、spec 和台账都写到磁盘上，再改第一行代码。

1. **建 Epic。** 已有对应且还开着的 Epic 就在它的目录里补 `ledger.md`；没有就按 `SKILL.md` 的路径建 Epic 目录、`spec.md` 和 `ledger.md`。不用先征得用户同意，在汇报里说为什么建。用户要求无痕迹时（见 `SKILL.md`「无痕迹例外」）不建 Epic，台账和已定方案写在仓库外的临时目录，同样按下文的写法写，汇报里给出路径，并说明换机器或清掉这个目录后就接不上。
2. **把已定的写进 Epic spec。** 本会话（包括之前的讨论）已经谈定的方案、必须守住的约束、被否掉的方案及原因，写进 spec 的「已定方案与必须守住」。写法按 `SKILL.md`「记录写给下一个 agent」里「用户的要求与拍板」那一行。还没定的写进「未确认问题」。
3. **列台账。** 台账要全，所以从事实源列，不凭理解列：
   - 有旧实现或对照物的任务（迁移、重写、移植、对齐），用命令从旧实现里机械列举，比如文件、路由、页面、测试 ID、命令行子命令、挂载的组件、配置项、协议消息。选一种粒度，让每一行能用一次观察判断做没做。列举命令写在台账开头，以后可以重跑。
   - 没有对照物的新功能，把用户的原话逐句拆开，每句至少对应一行；spec 里的验收场景也各占一行。
4. **切单元。** 一个单元是台账里的一组行。大小按一个会话能做完并验证来估，结束时处在可以验证的状态。风险最高的单元先做，手法见 [do](do.md)「穿刺」。
5. **攒一次范围问题。** 列台账时发现想标「不做」的行，攒在一起问用户一次，带推荐；做到中途才想标「不做」的，那一行先留 `没做`，在下次汇报里问。没有运行时行为的行（类型定义、测试辅助、构建产物）直接标「不适用」并写理由。

## 台账

`ledger.md` 是 Epic 唯一的推进状态文件，Epic spec 的推进视图链接它，状态只在台账维护。

开头写三样：列举命令或拆分来源；结论取值的说明；一句提示「接着做或改这张表之前，先读同目录 spec.md 的已定方案与必须守住」。正文一行一项：

| 项 | 单元 | 结论 | 证据 |
|---|---|---|---|

结论只取下面五个值：

- `没做`：列出来以后的初始值。
- `在做`：单元开工前，把它的行改成这个值。
- `做了`：证据写这次跑过的命令和结果、测试名或截图路径，有 commit 就附上。检查没走到改动真正生效的路径（缺凭据、缺真机）的，写清缺什么，并列进汇报末尾的「需要你看的」。
- `不做`：写清是谁定的，用户原话或 decision 的路径。
- `不适用`：只用于没有运行时行为的项（类型定义、测试辅助、构建产物），写理由。

## 三个重读时点

在下面三个时点，先重读 Epic spec 的「已定方案与必须守住」、台账开头和当前单元的行，再继续：

1. 开始一个单元之前。
2. 说一个单元或整个 Epic 做完之前。这个单元的行全部是 `做了`、`不做` 或 `不适用` 并带证据，才算做完。说整个 Epic 做完之前，按台账开头的列举命令或拆分来源重新列一遍，和台账逐行对照，多出来的项补进台账。
3. 发现上下文是从压缩摘要接着来的时候。

## 偏离与范围

- 实现中觉得已定方案行不通，或者要违反必须守住的约束，停下来问用户，带上证据和推荐。用户改了主意，就更新 spec 里那一条，写明日期和原话；这条拍板另有 decision 的，按 `templates/entities/decision.md` 立一条新 decision 取代它。
- 对不上任何台账行的改动不做，在汇报里列为顺手发现。确实属于目标、只是台账漏掉的，先补进台账再做。
- 一个单元在一个会话里没做完，就在台账开头写接续点：还剩哪些行、下一步从哪开始；下次开工前把剩下的切小。
