# Note：记录可复用知识

## 背景

把“这事以后还会用到”放到未来真正会读取的位置，但不要把 `byissue/notes/` 写成垃圾桶。

**去处只有一个：`byissue/notes/`。** 拍板进 `byissue/decisions/`（三条件见 `SKILL.md`）；notes 收的是做法、坑点与操作经验。

**写进 `notes/` 是这条知识的终点。** 遇到确实值得每次启动都知道的规则，照常写进 notes，然后**告诉用户**：这条如果想每次启动都生效，可以自己往 `AGENTS.md` 加一行索引。说到为止，不代劳、不追问。边界归 [SKILL.md](../SKILL.md)。

## 原则

先做“六个月测试”：半年后仍会影响判断或操作，而且很难只从代码、git diff、README 重新看出来，才值得写。代码已明说的细节、一次性流水、临时情绪，不要沉淀。

项目主线真相进 project spec；变更历史留 issue/epic；未知流程走 [maketools](maketools.md)。

notes 按 [docs](docs.md) 组织：服务复用，不复刻聊天流水。

## 行动指南

先复用框架已注入的指令与当前上下文；查重时搜 `byissue/notes/`、相关 spec 与 issue/epic。已有相近 notes 则更新原文件（文末可加日期小节），不另开一条。

值得提示用户升为启动规则的典型：固定测试/构建命令、环境陷阱、目录禁区、长期命名约定。提示一句即可，文件仍然只写进 notes。

写 notes：`byissue/notes/{YYYY-MM-DD}-{名}.md`（直接放在 `notes/` 下，不按年/月分目录；命名见 `SKILL.md`）。标题和正文保留可搜关键词。

## 产物契约

`byissue/notes/{YYYY-MM-DD}-{名}.md`：读者先要**结论**，再要**何时适用**与**细节/证据**；见 `templates/entities/notes.md` 自检。标题与正文保留可搜关键词。一次一个主题；无关主题拆开。

## 收尾汇报

告诉用户写进了 `byissue/notes/` 的哪一条、是新增还是更新已有文件；若建议过升为启动规则，说明理由并把动手权留给用户。不要把文件清单当主要汇报，先讲这条知识未来会怎么帮上忙。

## 应用场景

用户说“记下来”“沉淀一下”“留个 note”“以后每次都要知道”，或一次工作暴露出可复用坑点、操作经验、调研结论、长期约束、命令/路径/环境陷阱时使用。

不替代 Close、Make Tools 或 Spec 模式。
