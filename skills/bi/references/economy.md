# 原则：实现经济性

实现经济性是在理解真实路径、目标和质量承诺以后，用系统能长期承受的最少新增复杂度完成变化。

## 先理解，再最小化

先顺清触发、责任、数据、状态、调用方和可观察结果，再判断哪一层能力足以完成变化。没有现状模型时，最小 diff 往往只是改在离症状最近的位置。

当前路径和约束已经足以判断时，选择第一个完整覆盖目标的方案并继续。

## 从不新增开始

按下面顺序判断，命中后停止：

1. 目标是否已经由现有行为满足，或能否通过删除、收窄需求、调整配置或修正规则完成。
2. 正确归属的现有模块、helper、类型、规则或项目模式是否已经提供能力。
3. 标准库、语言机制、浏览器、操作系统或数据库等平台能力是否完整覆盖。
4. 已安装依赖是否已经提供经过验证的能力。
5. 前面都不成立时，才编写完成当前目标所需的最小新代码。

几种方案同样小，选择边界行为更可靠、命名更清楚、调用方更省心的一种。“少写几行”不是独立目标。

## 在正确责任边界修一次

最小变化看系统总复杂度，不看当前文件的 diff。修改共享责任前搜索调用方和相邻入口，确认无效状态最早在哪里产生。能在共同归属处消除根因，就不要在每个调用方各加一个 guard。

能力属于现有模块时，把该模块做深。业务形状已经变了时，先按 [change](change.md) 重切归属再改行为。必要的结构调整可以先做，但必须直接降低当前变化的风险或认知负荷。

## 不为想象中的未来付费

没有真实变化维度时，不增加只有一个实现的接口、只有一个产品的工厂、没人会修改的配置、只转发调用的 wrapper，或“以后可能用到”的脚手架。新抽象、新接缝和新依赖都要能指出当前调用方、当前差异或当前风险。

当前确有已知上限时，把它写成有界简化：

- 已知上限：什么规模、环境或输入下会失效或明显退化。
- 升级触发：出现什么可观察证据时需要重新设计。
- 升级方向：届时替换哪一层能力。

没有上限或触发条件的“先这样”不是有界简化。

## 留下最小有用反馈

非平凡逻辑变化至少留下一个会在该行为再次损坏时失败的可运行检查。优先复用现有测试入口和用户可观察接口；一个窄测试、最小脚本或已有集成检查足够时，不新建测试框架。

涉及解析、分支、循环、金额、权限、信息安全性、安全性、迁移或数据丢失风险时，不能因 diff 很小而省略反馈回路。行为证明的表格和结果写入 [prove](prove.md)。

## 交付前清理自己的 diff

汇报完成前，对照 diff 只看本次新增的改动，删掉复述代码的注释、注释掉的旧代码、可信路径上为想象中的失败增加的兜底、绕过类型检查的抑制、可以提前返回拉平的深层嵌套，以及不符合所在文件习惯的命名和错误处理。

保留许可声明、外部平台或协议要求、公共接口契约、代码表达不了的约束链接和有界简化的上限说明。能落成类型、测试或检查的约束，优先落成检查。

清理不改行为。改完重跑本次验证，哪处清理让检查失败就撤回哪处。

没有真实对照基线时，不声称节省了多少行、成本或时间。最小实现的价值由责任面和可验证结果支撑。
