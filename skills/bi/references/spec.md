# Spec：维护当前真相与活规格

把当前现实或有边界的变化写进正确层级：项目主线进入 `byissue/spec/`，大需求活规格边界进入 `byissue/epics/{NNN}-o-{名称}/spec.md`。目标应用全景由 Vision 模式维护，不写进 Project Spec。

## 背景

真实开发不是“规格全清楚再实现”。通常先讨论出一个初始需求，形成 epic，切出一批 issue；做着做着发现规格补充、修改甚至推翻，于是回到 spec 重新整理，再调整本轮推进范围、生成新 issue、修改旧 issue 或关闭旧 issue。

Spec 模式的职责不是记流水账，而是维护“当前为什么这样”以及“一段变化现在怎样理解”。project spec 是现实主线；epic 是一条有边界的活规格和知识承载单元。Vision 中的目标不能提前进入 project spec；Epic 可以链接来源 Vision，但必须把本次准备兑现的切片重新收束清楚。

## 原则

**文档面向查看。** spec 写出来是给开发者看的。入口文档先让读者知道“这是什么”，再让读者选择“往哪里深入”。不要把 `index.md` 写成文件清单。

**只写代码里重建不出来的东西。** 这是 Project Spec 的准入判据。统一语言、边界与被排除的方案、长期质量约束与取舍、做与不做——这些的真相源在过去的讨论里，代码永远说不出来。而能力如何运作、架构地图、数据流叙述**不进** Project Spec：它们是代码的第二份表述，必然漂移，重建成本又很低，让读者直接去读代码更准。

Project Spec 因此是结构性必腐的一层，除非它只留重建不出来的部分。Epic Spec 不受这条约束——它描述的是**还不存在**的东西，代码里没有对应物，所以不会漂移。

**spec 是树，不是二级目录。** 简单内容一篇写完；复杂子系统可以继续拆层。只要一个目录下有多篇文档，就要有该层 `index.md` 统领方向感、统一语言和阅读路径。

**统一语言就近放置。** 不另起 domain 体系。术语放在离它生效范围最近的 `index.md`；术语太多时可拆相邻 `terms.md`，但必须由该层入口指过去。

**写考量，不写流水。** 不创建 `changes.md`。规格变化要呈现为当前需求、架构考量、被排除方案、边界和影响，而不是“某时从 A 变成 B”。够格的拍板（三条件见 `SKILL.md`）另立 `byissue/decisions/` 保持可寻址；spec 叙事只留当前仍然成立的结论。

**核心理解不引用代码。** spec 的正文按概念、边界和取舍组织；代码路径、函数名和命令结果只在给某条结论作证据时出现。读者不该靠读代码路径推断需求与取舍，也不该指望 spec 告诉他代码长什么样。

**主线只收毕业结论。** epic 过程中的变化先进入 epic spec；epic 下 issue 关闭也先回写 epic spec。只有 epic 人工关闭后，才把稳定结论合并回 project spec。

**Project Spec 不做能力落点地图。** 不要维护「哪个能力在哪、怎样运作」的索引层：找代码是廉价的，而索引会跟着代码漂。能力的名字由统一语言承载，怎样运作由代码承载。个别代码路径可以作为某条结论的证据出现，但 spec 不承担导航职责。

已关闭 Epic 与 Issue 是设计历史和证据，不是当前真相的替代品。

**目标世界由 Vision 承担。** Project Spec 不再保存“将来想做什么”的产品全景。Vision 与当前现实不同是正常差距；Epic 负责圈住一次缩小差距的变化。发现目标方向需要调整时切换 Vision，不在 Project Spec 或 Epic 中静默改写。

**质量约束属于规格，不属于检查表。** 只有长期有效、会约束后续设计或验收的质量目标与取舍才进入 project / epic spec。按九特征统一语言，但不列九项“满足 / 不适用”；一次变化的测试结果、基准数据和执行证据留在 issue。

**UI 规格把关系画出来。** 涉及空间关系、信息层级或多状态交互时，按 `ui-spec.md` 提供可版本化的图与标注。Project Spec 只描述当前稳定界面；Epic Spec 明确区分当前与目标。图说明布局和关系，文字说明行为、边界和取舍，两者冲突时必须消歧，不能让实现者猜。

**Epic 是活规格边界。** 只有跨模块、会多轮变化、会分批 issue、或规格会在一个可圈住范围内反复演进时，才创建 epic。它不是任务桶，也不是 project spec 的缩小版；它负责让变化留在一个人类能 review、AI 能持续对齐的范围里。

**Epic spec 同时承载当前推进。** 不必等整个 epic 全局完美。某一批目标、范围、依赖和验证足够清楚，就在同一个 `spec.md` 的“当前推进”中标出可推进范围、**epic 内直接推进**的切片、按需 issue、暂停或废弃项和剩余阻碍。推进视图不是独立真相，也不替 issue 写实现设计。

## 行动指南

先判断目标层级：

- 项目长期真相、独立小需求沉淀、全局统一语言或架构方向 → 更新 `byissue/spec/`。
- 大需求、跨模块变更、会分多批 issue、规格会反复变化 → 更新该 Epic 目录下的 `spec.md`（路径与编号见 `SKILL.md`；首个所属 Issue 创建时再建同目录 `issues/`）。
- 跨越多个 Epic 的目标产品全景、候选方向或互斥实验 → 切换 Vision。
- 没有现成 epic 但明显需要一条变更线 → 先说明为什么需要 epic；用户同意后创建 `{NNN}-o-{名称}/` 目录型 epic。

更新 project spec 时，先读 `byissue/spec/index.md`。按阅读路径找到最近的子层；缺少合适位置时，先补该层 `index.md` 或新建子层入口，不要把结论散落成平级文件。

每条计划写入的结论先过准入判据：**它能从代码重建吗？** 能，就不写，让读者去读代码；不能，才写。典型的「不能」是：这个词在本项目指什么、边界为什么划在这里、哪些方案被排除过、哪条长期约束会约束后续设计。

按判据筛完，Project Spec 通常很短，也就不太需要分层。内容确实多到一个文件读不下去时再拆，拆了就给该层 `index.md`；不要为了形式把简单主题拆成文件树。

更新 epic spec 时，先读该 epic 的 `spec.md`、同目录 `issues/`、它明确引用的相邻材料、来源 Vision 和相关 project spec。epic spec 要说明它从 Vision 摘取什么目标、相对 project spec 改变什么、为什么现在这样设计、哪些术语只在本 epic 生效、哪些范围本轮可推进、哪些还悬着。

写入 spec 时，先完成面向人的核心理解，再按需补证据索引。核心段落不要把文件、类、函数或命令当主语；它们只说明“这个理解可以从哪里验证”或“执行者到哪里落手”。如果一个章节只能按代码目录命名，先问它对应什么使用场景、能力或决策路径。

涉及质量要求时读取 `quality.md`：记录特性或子特性、适用条件、具体约束和关键取舍。指标阈值、兼容策略、成本显著增加或目标冲突由用户确认；普通工程约束可以根据已确认需求和证据直接维护。Epic 切 issue 时，只把与该 issue 相关的质量约束继承过去。

涉及 UI 结构时读取 `ui-spec.md`。区域位置、分栏分组、页面关系、控件共置、关键状态或响应式结构会影响需求理解时必须画；纯文案、设计 token 或无空间歧义的单控件变化不强制。Project Spec 的图标记为当前，Epic 的图标记当前 / 目标，截图和原型只放相关材料或证据索引。只画关键关系，图下标注角色与入口、交互与状态、稳定约束和仍属示意的部分。

遇到未知系统、术语、角色、状态和流程，先查 `byissue/`、README、代码、历史 issue/epic、notes 和 project spec。查不到或存在多个可能含义时，向用户提带证据的问题；需要顺清“触发如何产生结果”且无法在当前上下文紧凑解释时，先做**现状说明**，不够则建 **Explore issue**（见 [explore](explore.md)）。

## 产物契约

project spec 默认入口是 `byissue/spec/index.md`，使用 `templates/entities/project-spec-index.md`。子层入口用 `templates/entities/spec-section-index.md`。

epic 的权威入口是该 Epic 目录下的 `spec.md`（路径形态、关闭改名与编号见 `SKILL.md`），使用 `templates/entities/epic-spec.md`；有所属 Issue 时增加同目录 `issues/`，所属 Issue 均写入该目录。不要创建重复职责的 `index.md`、`plan.md` 或 `changes.md`。材料复杂时可增加按内容命名的相邻文档，但不能承载第二份状态或计划，并必须由 `spec.md` 说明为什么读、何时读。

`spec.md` 须让读者能回答模板自检中的问题（要改变什么、当前方案、架构与质量取舍、可推进/暂不推进、未确认项、关闭与合并候选等）；**信息职责**优先于固定章节名，内容少可合并，禁止空章凑模板。存在长期质量约束时写清适用条件、具体目标和取舍，不生成九项空清单。

推进视图只记可推进范围、直接切片结果与证据索引、issue 链接、暂停/废弃与阻碍；不复制 issue 正文或实现设计。

## 收尾汇报

先讲 spec 更新后的当前判断：这次澄清了什么、为什么现在这样考虑、哪些质量约束会影响后续 issue、哪些范围本轮可以推进、哪些仍悬着、是否影响已有 issue。再给文件路径作为索引。

## 应用场景

更新 project spec、创建或调整 epic spec、规格补充/修改/推翻、PRD/SE 文档需要落到开发者能读的规格、实现中发现原规格不成立时使用。

不适用：整个目标应用仍在构想或整理时切换 Vision；局部目标还在脑暴或需要初步规划时切换 Talk；单个 issue 的实现方案切换 Design；当前系统怎样工作仍说不清时切换 Explore；代码执行切换 Do。
