# Close：关闭与沉淀

关闭 issue 或 epic，把仍成立的结论**毕业**到正确层级；Epic 关闭时检查来源 Vision 的实现状态与链接。

**关闭 ≠ 完成。** 完成指实现与验证已达成目标；关闭须用户授权收尾（“关闭 / 收尾 / 做完并沉淀”等）。Git 契约见下与 `SKILL.md`。

**关闭即终态，文件留在原树原位。** 状态由文件名（`x`/`d`）表达，检索靠递归扫描。

## 背景

复利在关闭时的回写：issue 留执行历史；epic spec 留活规格边界内的当前理解；project spec 留主线真相。回写层级见 `SKILL.md` 毕业规则与下文。

## 原则

**先确认可以关闭。** 目标达成、范围未暗扩、已选质量目标均有相称证据。Epic 必须由人确认关闭，不能因 issue 看起来都完成就自行关闭。

**只沉淀仍然有效的东西。** 不把事项全文搬进 spec；流水与中间判断留原事项。

**任何改名都先修引用。** 状态写在路径里，所以改 issue 文件名、Explore 目录名或 Epic 目录名都会打断每一条指向它的全名引用。改名前用**确切的旧全名**（去掉结尾的 `.md`）做一次固定串搜索：`grep -rnF --exclude-dir=.git "<旧全名>" .`——`--exclude-dir=.git` 必须带，否则 `.git/COMMIT_EDITMSG` 与二进制的 `index` 会混进命中，残留核对永远清不干净。命中要**逐条看**：名字两端紧贴的字符都**不是名称字符**（字母、数字、`-`、`_`，或**文字的字**——中文、假名都算；标点、括号、引号、逗号顿号、空白都不算），就是本事项的引用；名字后面**直接续着更多名字**（没有分隔符隔开，如 `训练计划` 后面直接是 `日历`），是**同日同前缀的另一个事项**，跳过。**下面三条跳过情形优先于这条主判据**——命中任一条就跳过，不要因为两端都是分隔符就当成本事项：**命中处的完整路径若指向别的 issues 树**（某 Epic 的 `issues/` 下，而你关的是根树那个，或反过来），是**同名同日的另一个事项**——跳过。关 `.md` 文件时，旧全名后面**直接跟 `/`**（被当作目录名用，如指向同名 Explore 目录的 `index.md`）的，是**同名异形态的邻居**——跳过；关目录时，后面直接跟 `.md` 的同理。命中处的路径在**依赖或构建产物目录**里（`node_modules`、`dist`、`.venv` 之类——`grep` 不读 `.gitignore`，这些目录会混进命中）的，不是引用，跳过不改、不计入 N 处。逐**处**判断，各看各的路径：同一行里可能既有本树命中又有跨树命中，不能按整行一刀切。判不准就分两种：处里带路径的，把该路径指到的文件 `ls` 一下——**文件名与旧全名一致、且在你正改的那棵树里**，才是本事项（只看树不看名字会把同树的异名事项误认成命中）；行里没有路径（裸提及）的，当作本事项的引用一并更新——漏改一条裸提及会悬挂，多改一条有路径可查的会写错，两害相权裸提及先按本事项处理。改完再 `grep` 一遍旧名核对，剩下的命中分三桶：在**别的树**里（名字以旧全名开头的同名、续名事项），或**依赖与构建产物目录**里的，是正常残留，不要清掉；是**同树里名字以旧全名开头、但不是本事项**的邻居（还开着的 `-o-login-v2`、同名的 Explore 目录）的，同样不要动；还有**指向本事项**的，才是漏改，补上。把该改的更新到新路径，并在收尾汇报里报「找到 N 处引用，已更新」或「0 处」，**不要静默跳过**。实现时逐**处**改写：同文件里跳过项与命中项可能同行，对整个文件全局替换会把该跳过的一并改掉。

为什么不用正则边界：`(ff-)?` 会命中同日的常规项，`(\.md|/)` 会漏掉裸提及，`[^A-Za-z0-9_-]` 又会把中文续写当成边界（关 `…-o-训练计划` 时命中 `…-o-训练计划日历.md`——正是「写出不存在路径」）。名称可以是任何文字，没有一个字符类能划对边界；**固定串加逐条看**才是稳的。

**毕业是筛选，不是搬运。** 独立 issue → project spec；epic issue → epic spec；epic 关闭 → project spec 并检查 Vision。但回写前先过 Project Spec 的准入判据（见 [spec](spec.md)）：**能从代码重建的不写**。多数 Epic 关闭时真正该进 Project Spec 的只有几个词、一两条边界和被排除的方案，而不是一节能力说明。

筛掉的内容不是丢失：它在代码里。Epic 链接保留为历史、证据或深入设计的阅读入口。普通 issue 不更新 Vision。notes / tools 按复用价值分流。

**只按事实更新 Vision 状态。** 实现程度与链接可更新；目标内容或候选关系要变时须用户确认，否则记录偏差。

**spec 写当前为什么这样。** 不写“某天从 A 改到 B”的流水。

**只按承诺检查质量。** 不重开九项清单。关键遗漏 → 回 Design 补目标与响应，再 Do；不能在关闭结论里临时降级。见 [quality](quality.md)。

**有界简化必须仍有界。** 检查上限、触发未发生、未削弱目标与承诺。稳定产品边界 → spec；维护坑点 → notes；触发已发生且阻碍目标 → 回 Design/Do，不能以“后续再做”关闭。见 [economy](economy.md)。

**UI 按真相层级毕业。** 见 [ui-spec](ui-spec.md)。

**核心理解不引用代码。** 代码路径与命令留 issue/notes/证据索引。见 [docs](docs.md)。

**先守组织再写内容。** 从 `byissue/spec/index.md` 找路径；缺位置先补入口，不散落平级文件。

**探索文章按渐进式披露毕业。** 不是原样搬家；稳定现状机制说明按 Spec 结构安置。

## 行动指南

### 读取关闭上下文

- issue：用户给路径则读该文件/目录；否则递归搜索根 `byissue/issues/` 与各 Epic 的 `issues/`，按名称或完整路径消歧
- epic：读权威 `spec.md`、同目录 `issues/`、明确引用的相邻材料

写入或暂存前确认目标事项、将回写的 spec/notes/tools、以及要提交代码的当前版本。

### 关闭 issue

路径规则：把目标 Issue 文件名或目录名中的 **`-o-` 改为 `-x-`（交付关闭）或 `-d-`（放弃关闭）**，保留日期前缀、可选的 `ff`、名称与所属 issues 树不变。例如 `2026-09-21-o-fix-login.md` → `2026-09-21-x-fix-login.md`；放弃：`2026-09-21-o-fix-login.md` → `2026-09-21-d-fix-login.md`；Epic 内 `issues/2026-09-21-o-ff-toolbar.md` → `issues/2026-09-21-x-ff-toolbar.md`；Explore 目录 `issues/2026-09-21-o-auth-flow/` → `issues/2026-09-21-x-auth-flow/`。放弃用的是同一个字母位置：`-o-` → `-d-`，Epic 目录同理。不要因关闭子 Issue 改 Epic 目录状态。

**改名前先修引用（见「原则」）。** 搜索串就抄现有文件名，例如关 `2026-10-13-o-ff-login.md` 时：`grep -rnF --exclude-dir=.git "2026-10-13-o-ff-login" .`。名字里有没有 `ff-` 段照着抄，**不要用 `(ff-)?` 之类可选写法**——它会把同日的常规项一起命中。

指向**已关闭**事项的引用永远稳定，只有指向**仍开着**事项的引用会随改名而断。范围限本项目 `byissue/` 与代码注释；跨仓库引用兜不住，不强求。

`-d-` 在正文记一句放弃原因，跳过毕业回写；检索时路径即可区分做过的与决定不做的。放弃后又想做的，新建新 issue，不复用原文件名。

- **普通 issue**：检查目标、范围、质量目标、执行记录与验证；有界简化则检查上限/触发/方向。缺记录或证据 → 回 Design/Do。
- **ff issue**：检查四答是否齐全（做了什么 / 改了哪些 / 验证 / 对 `byissue/` 的影响）。真相失效须已同步 spec 或明确标漂移；不要求完整质量清单与实现设计。同会话快改已直接落 `x-ff` 的，无需再关一次。
- **Explore issue**：不要求业务代码执行记录。须能讲清触发—过程—结果，相关责任/数据/状态有证据，未知显式标出；有具体变化时影响已分层。未达“足够行动” → 继续探索，不进 Do。
- **dropped issue**：路径 `-d-`；确认放弃原因已记录；质量证据与毕业回写均跳过。

### 沉淀收割（提交前必做）

把整个推进过程产生的材料与新获知的经验过一遍：目标事项的执行记录、验证、顺手发现、「对 `byissue/` 的影响」、Explore 的证据层，以及途中新暴露的隐含约束与踩坑经验；同时对照既有 `notes/` 与 `spec/`，检查是否有同主题记录需要追更、或已有描述因本次改动而过期。**列出沉淀候选并给出建议，无候选明说「无」；裁决必须在提交前完成。**正常流程在收尾汇报中列出；用户先要求提交 / 推送 / 开 PR / 合并、候选仍未裁决的，同轮列出并请求授权，落盘随同次提交走；合并后才冒出的新候选照常提出，是否再起一笔提交由用户裁决（时序契约见 `SKILL.md` 提交表格与 [do](do.md)；快改见 [fast](fast.md)）。

自检盘点时问事实问题：「这次撞上了哪些仓库外部的事实——外部系统行为、平台差异、依赖的真实语义、失败过的尝试、被排除的方案？」向用户呈现候选的格式见 `SKILL.md`「提问必须带建议」。

每条候选写清：是什么、建议去哪、为什么（或为什么不建议）。去向按下面的归属表，但**判断由这一步产出，不靠自发想起**。

按物理归属回写，路径是权威来源：

- `type: ff`：默认不强制大段毕业；按「对 `byissue/` 的影响」执行或确认；坑点可进 notes
- 根 `issues/` 下的独立事项：稳定结论 → project spec
- `type: explore`：独立 Explore 经用户认可后，稳定现状机制说明 → `byissue/spec/` 并更新 `index.md`；Epic 内 Explore 先回写所属 epic spec；影响分析留 `related_issue`；证据与已排除理解留 Explore issue
- Epic 的 `issues/` 下：结果、验证、仍有效约束、推进变化与毕业候选 → 该 epic `spec.md`

长期决策 → `byissue/decisions/`（模板 `templates/entities/decision.md`；满足三条件时立碑，被取代时不改写旧文，指向新决策）；坑点 → notes；稳定工具 → tools。写入边界见 [SKILL.md](../SKILL.md)。

### 关闭 epic

仅用户明确要求时。确认：关闭条件满足；epic 内直接推进已有足够验证；同目录 `issues/` 中的事项已关或明确废弃/移出；质量约束有证据或保留为后续约束；毕业候选足够稳定。

先筛出 Epic 成果里**代码重建不出来**的部分，写进 `byissue/spec/`，再关闭 Epic。该进去的是：这条线引入或改变了哪些词、边界为什么落在这里、哪些方案被排除过、后续变化必须遵守什么长期约束、哪些范围明确不属于它。**不要**写这个能力怎样工作、由哪些模块承担、数据怎么流——那些读代码更准。也不要原样搬运 issue 列表、实施过程或测试流水。

写入后逐项检查：

- 写进去的每一条都经得起一句追问：这能从代码重建吗？能，就该删。
- 已关闭 Epic 中仍有价值的内容保留为设计历史、验证证据或被排除方案。
- Project Spec 没有遗留与实现冲突的旧表述；活跃但尚未关闭的其他 Epic 不被误写成已毕业的稳定契约。

确认上述回写后，记录 Project Spec 中的具体合并章节；Epic 目录名 `-o-` → `-x-`（交付关闭）或 `-d-`（放弃关闭），日期与名称不变，内部 `issues/` 整体随目录保留，不重命名、不因 Epic 关闭改子 Issue 状态。有来源 Vision 则按事实更新实现程度与链接；改目标内容须确认。

### 提交关闭变更

在 git 仓库中，关闭改名与毕业回写作为变更的一部分，与业务代码在同一次提交中完成（业务代码、目标 issue/epic、project/epic spec、notes/tools）。代码已被先行提交时，关闭单独成笔。

提交前 `git status --short`，只暂存相关文件。无关脏改不碰；同文件混有无关变更则停下说明。不 amend / rebase / reset。

## 产物契约

关闭 issue：

- 常规 issue 写清关闭结论：判断、验证摘要（含质量证据）、回写位置、遗留事项；ff 以「对 `byissue/` 的影响」为准，可无长关闭结论
- 路径 `-o-` → `-x-` 或 `-d-`（日期与名称不变）

关闭 Explore issue：另更新 spec 阅读路径，并在 Explore 入口记录迁入结果。

关闭 epic：

- Project Spec 已写入筛选后的结论：词汇、长期边界与取舍、被排除方案；能从代码重建的部分已刻意留给代码
- 记录合并到 Project Spec 的具体章节与已检查/更新的 Vision
- 目录 `{YYYY-MM-DD}-o-{Epic名}/` → `{YYYY-MM-DD}-x-{Epic名}/` 或 `{YYYY-MM-DD}-d-{Epic名}/`；不删除目录。**改名会打断指向该目录下任何路径的引用**（`spec.md`、该目录 `issues/` 下的任何事项、跨 Epic 写出的完整路径都算），改名前按「原则」先修：`grep -rnF --exclude-dir=.git "{YYYY-MM-DD}-o-{Epic名}" .`

遗留事项应成新 issue 或留在 epic 当前推进/阻碍中，不藏在关闭结论里；仅用户明确要求时建新 issue。

## 收尾汇报

先讲为何可关、质量证据、沉淀裁决结果（候选、去向，无候选则明说；裁决发生在提交前，合并后收尾报结果，合并后才冒出的新候选照常提出）、实际沉淀到哪一层、改名影响了几处引用（0 处也要说）、Epic 时如何同步或保留 Vision、是否已 commit。路径与 commit 作证据。

## 应用场景

实现验证完成后关闭 issue；Explore 经确认合并 project spec；bug/feature 关闭沉淀；用户确认后关 epic。

不适用：代码未完成 → Do；设计缺口 → Design；规格仍变 → Spec；默认不推送不部署。
