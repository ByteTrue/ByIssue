# 原则：Grilling（多轮拷问）

不停地问，直到和用户达成同一份理解。**这是纯访谈循环：不写文件、不建事项。** 落盘由调用它的姿态负责（Talk / Vision / Design）。

## 背景

模型面对含糊需求的强默认是「给三个选项 + 一句推荐」然后收工。这看起来是对齐，其实是把决策树压扁成一层：用户挑完一个，挂在它下面的决策一个都没被访问过。

**选项是产出，不是拷问。** 真正的对齐要求用户回答足够多的问题，多到他自己的认知被改变。所以本文件全部写成祈使句——描述句在这里不会被执行。

**在别的姿态里跑 grilling 时，那个姿态的任务感会被误读成「可以继续推进」的许可。** 这是本技能最常见的失败方式：Talk 想收出口、Design 想交方案、Do 想动手，于是访谈被压缩成一轮，或者干脆自己把自己的问题答了。姿态的目标不是提前结束访谈的理由。

**开始提问前先读完本文件。** 凭印象访谈的结果是一次性倒出所有问题、不带推荐、没有轮次——那不是在拷问，是在问卷。

## 原则

### 建一棵设计树

把讨论对象映射成**设计树**：每个决策分叉出挂在它下面的决策。「先做本地缓存」分叉出缓存键怎么定、失效策略、内存上限、多进程怎么办。按轮次走这棵树。

**树留在脑子里，不落盘。** 它每轮都被答案重塑；写下来只会造出第二个真相源，然后你要维护两份。

**前沿是你的判断，不是算出来的图。** 你可能把两个问题放进同一轮，答完才发现其中一个答案本该改变另一个。这时**在下一轮重开那个分支**，明说「你刚才的答案让 X 需要重问」，不要装作原来那轮没问题。

### 每轮问整个前沿

**前沿 = 所有前置已经定了的决策**：现在能诚实问出口、不需要猜一个还没听到的答案的那些问题。

一轮把**整个前沿**问完，逐条编号并附推荐答案，然后**停下来等用户答完再进下一轮**。

**不是一次问一个，也不是一次问全部。** 前者要四十个来回，后者会问出依赖尚未听到的答案的问题。

同一轮里不得有两个互相依赖的问题。答案取决于本轮某个还没答的问题，它属于**下一轮**。

一轮的形状（标题、正文、推荐各占其位，问题之间用 `---` 隔开，别连成一片）：

```text
**问 1｜缓存键怎么定**：正文可以有多段，也可以把几个互斥选项列在这里。
**建议：** 用 `userId + resourcePath`。理由一句话。

---

**问 2｜失效策略**：正文……
**建议：** ……
```

**标题是必需的**：它迫使每条问题落在一个决策上，也让用户能按编号回答（「1 是，2 选第二个，3 不是，因为……」）而不用把问题抄回来。推荐答案单独占一行，别埋进正文。

用户明确要求「一次只问一个」时照办，这是他的节奏不是你的；其余规则不变。

### 每轮重算前沿

答案会重塑树：定下来的决策把前沿往外推，解锁原先被挡住的问题。**下一轮是重算出来的，不是预先写好的。**

每轮开头用一句说明上一轮的答案解锁了什么。这是唯一可观察的进展信号：后面的轮在问第一轮根本问不出的东西。

### 事实自己查，决策交用户

前沿上某个问题需要环境里的事实（代码、依赖、配置、外部 API）时，**起一个 subagent 去查**，或直接查。不要把任何你自己查得到的东西问用户。

**不要等它回来再发这一轮。** 正在跑的调查就是一个尚未确定的前置，所以只有依赖它的那些问题等着，前沿上其余的问题现在就问。

**决策是用户的：一条条交给他，然后等。** 替用户把决策做掉的 grilling 是坏掉了，不是宽松地执行。

### 同步磨术语和事实

访谈进行时，这四件事**当场做**，不要攒到收束：

- **与统一语言顶撞。** 用户用的词和项目已有词汇（`byissue/spec/` 的统一语言、代码里的命名）冲突时立刻指出：「spec 里 X 定义成 A，你现在指的像 B，到底是哪个？」
- **磨模糊词。** 用户用了含糊或多义的说法，提一个精确的候选词：「你说『账户』，指用户还是客户？这是两个东西。」
- **编具体场景压边界。** 讨论概念之间的关系时，现编一个探边界的场景逼用户把话说准：「如果同一订单里一半可退一半不可退，这条规则怎么算？」
- **拿代码对照。** 用户陈述系统怎样工作时，去核对代码是否同意。发现矛盾当场摆出来：「代码里取消的是整个订单，但你刚说支持部分取消。哪个对？」

**问出来的东西当场接住，别让它蒸发。** 一个术语定下来，就提议写进它生效范围最近的统一语言（放哪、怎么写由 [spec](spec.md) 定）；一个决策同时满足「难以逆转 / 离开当时语境会觉得奇怪 / 存在真实备选」三条，就提议立碑（契约见 `SKILL.md`「什么内容可以写到哪一层」）。提议不等于直接写：Talk 姿态下用户确认前不落盘。攒到最后再一起回忆哪些词定过，一定会漏。

### 前沿为空才算完

终止条件：设计树每个分支都被访问过，没有静默假设，**并且用户确认理解一致**。

这个条件是用户侧可判定的——前沿为空必然意味着用户已经答了很多轮。

**不设轮数上限，不设问题数上限。** 有的计划三个问题就够，有的要五十个；固定天花板要么截断难例，要么在易例上显得随意。校准：**46 个问题落在 4 轮里是普通会话**——问题数高、轮数低才对。

问到两百条通常是范围太大。先把它拆小，再分别 grill；超长会话里上下文快满时，问题质量本身会开始下降。

### 这几条是假信号

以下每一条看起来像「已经问清楚了」，实际是把提问偷换成了自我陈述。**都要真的问出来：**

| 假信号 | 真实含义 |
|---|---|
| 「最大未知已标出」 | 标出 = 我承认不知道，不是我问出来了 |
| 「接口未清，标待确认」 | 同上，而且把成本推给了实现阶段 |
| 「做什么有轮廓」 | 我给过三个选项，那是我的轮廓，不是用户的 |
| 「真问题一句话」 | 我总结得出来，不等于用户确认过 |

### 用户说停才停

前沿为空不等于可以动手。等用户确认「我们理解一致」再进入下一步——这道确认门正是为了挡住「问题问完了就自己开工」。用户还在提新判断、纠正或问题时继续问，即使出口草案已经成形；被授权的动作（查一个事实、落一个文件）做完回到访谈。

唯一的例外：争的是**事实**且半小时内能验证时，动手查比继续聊更省。这时中断访谈去查证，回来接着问。

## 谈不出来的问题

有些问题靠对话解决不了：「一个长表单还是分三页」「这个交互该是什么手感」。撞上就停止 grilling，做一个一次性原型或草图让用户有东西可反应（UI 见 [ui-spec](ui-spec.md)），回来一句话定掉。

硬聊这类问题是会话膨胀的主因：我反复换措辞，你反复猜，范围跟着不确定性一起涨。

## 用对了的样子

- 一轮是编号列表，每条有标题、正文、单独一行的推荐答案，问题之间有分隔；用户能按编号回答。
- 一轮之内没有需要先答另一条才能答的问题。
- 后面的轮在问第一轮问不出来的东西，且每轮开头说清了是什么答案解锁了它们。
- 能查的事实自己去查（读文件、起 subagent），而不是问用户；后台调查不拖住本轮。
- 用户用了和 spec / 代码不一致的词，当场被顶回来。
- 结束时停下来请用户确认理解一致，而不是直接开工。
- 问题数高、轮数低。

## 应用场景

Talk、Vision、Design 需要把模糊想法问清楚时。它是这些姿态**共用的访谈 primitive，不是排期里的一个步骤**：需要访谈就调它，别在每个姿态里另写一套提问方式。

不适用：目标已经明确只差实现（→ [fast](fast.md) / [do](do.md)）；用户明确要快；只需要报告现状（→ [explore](explore.md)）。
