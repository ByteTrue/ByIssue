# 快改：小改默认通道

小需求、用户要快、或一次可做完的低风险改动走这里。快改的全部产出是三样：代码、验证、一份四答 `ff`——动手前轻扫 `byissue/`，动手后落 `ff`，追溯靠它，仪式到此为止。

用户只给明确小目标、且未要求常规 issue 时，这里是默认出口；规模配不上时切常规通道（见文末）。

**例外：** 用户明确说不要痕迹 / 别写 issue / 别落盘 ff 时，只实现验证、跳过 `ff`；真相失效仍应同步 project spec 或标漂移。其余情况一律落 `ff`。

## 原则

**小改默认走这里。** 两层保护：改前指到制度记忆；改后留下最简 `ff` 痕迹。

**入口轻，出口有纪律。** `ff` 在代码与验证完成后创建——动手前它没有内容可写；同会话做完可直接落 `NNN-x-ff-名称.md`。

**命中的 spec / decision 是约束。** 违反时先改 spec（须授权），或换一种实现方式。

**复杂就跳车。** 切回 Design / 常规 issue，比硬推快改便宜。

## 归属与模板

- 归属按「是否明确推进某 Epic 边界」判断：是 → 该 Epic 的 `issues/`；否 → 根 `byissue/issues/`。代码路径碰巧相邻，构不成挂靠理由。
- 模板：`templates/entities/ff-issue.md`，`type: ff`。路径形态与编号规则见 `SKILL.md`。

## 行动指南

### 1. 改前（开工协议的轻量版）

对整个 `byissue/` 做路径浏览 + 关键词 grep，再按命中深读（协议见 `SKILL.md`「开工协议」）：

1. **这块以前栽过吗？** → `notes/`、递归检索根与各 Epic 的 issues（含 `-x-`、`done/` 与历史 `ff`）
2. **有没有已拍板的写法/边界？** → **project spec**（重中之重）+ 相关 epic spec + 相关 decision

本会话同主题已扫过且无新写入可复用。没命中时按自己判断写很正常。

快改的现状说明，一句话能说清触发→结果即可；说不清或跨多边界 → 跳出快改。

### 2. 实现时守住的红线

- **先想放在哪儿**：归属仍对，扩展该模块；业务形状已变，先抽/重切再改。过载 if-else、顺手文件，都是归属错误的信号。
- **范围以用户要求为界**：提前抽象、配置开关、工厂、无关兜底，等真实需要出现时再加。
- **只动该动的**：同文件无关丑代码记入「顺手发现」留待后续；为目标服务的最小结构步（抽取到正确归属）属于本次。
- **默认最少总复杂度**：衡量对象是系统总复杂度；diff 大小与文件形状只是表象。细节见 [economy](economy.md)。
- **反射信号就停**（任一条出现就评估是否跳出）：改动跨 3+ 能力边界；要引入新术语或冲突统一语言；要动 project/epic 已定模块/产品边界；范围翻倍；文件/函数已明显过载还在硬塞。停的对象是范围失控；该做的抽取照做。

### 3. 验证

跑最相关检查；跑不了就写清手测步骤。用户确认效果 OK 后再落 `ff` 痕迹（用户明确说不用确认，则验证通过即可落盘）。

### 4. 回写 `ff` issue（默认必做；例外见开头）

先判断归属，再从用户请求抽 2–4 词英文短横线作 `{名称}`，在所属 issues 树取下一 `NNN`。

同会话已完成：直接在所属树写 `{NNN}-x-ff-{名称}.md`，`status: closed`。
需跨会话：先 `{NNN}-o-ff-...`，完成后在同一树改名为 `{NNN}-x-ff-...`。

正文只填：

- 做了什么
- 改了哪些
- 怎么验证的
- **对 `byissue/` 的影响**（必选其一：无影响 / 已同步 spec / 已知漂移 / 应升级流程）
- 顺手发现（可选）

写得轻：十几行通常够，四答之外的内容删掉。

真相失效且确定 → 同步相关 project spec 小节，并在「对 `byissue/` 的影响」写路径；不确定 → 标漂移并问用户。Vision 只由用户发起变更。

### 5. 收尾

告知用户 `ff` 路径已落盘（无痕迹例外则说明未写 ff 及原因）。默认停在提交前；用户同意时可做 scoped 提交：本次代码 + 该 `ff` issue +（若有）spec 同步。

可选一句提示（用户说不用则跳过）：是否把长期约束升进 project/epic spec；是否代为 commit。

## 什么时候跳出快改

任一情况停下，建议切 Design 或常规 issue：

- 改动涉及 3 个以上子系统/能力边界
- 需要引入新术语或与统一语言冲突
- 要改 project / epic 已定边界
- 用户追加需求使范围翻倍
- 需要多轮验收或正式质量承诺清单

已写代码在后续 Design/issue 中标「已部分实现」即可。

## 收尾汇报

做了什么、怎么验的、`ff` 路径（或无痕迹例外）、对 `byissue/` 的影响、是否建议 commit。顺手发现单独列出。

## 应用场景

小功能、小修复、布局微调、用户明确不要完整流程、以及默认的小而明确改动。

出口分流：模糊需求 → Talk；明确要设计 → Design；bug 走 Complain（默认定位试修，简单修好后仍落 `ff`，除非用户不要痕迹）；大边界变化 → Epic / 常规 issue。
