# 理解与审查

这个行动用于解释现状或审查用户给定范围。它默认产生解释和判断，不修改代码；用户明确要求改变后，再进入 [change](change.md)。

## 理解现状

从一个真实触发走到可观察结果，按渐进式披露展开：

1. 一句话说明入口、关键机制和结果。
2. 展开主路径的责任、数据、状态和副作用。
3. 只补与当前问题有关的分支和未知。
4. 给出代码、测试、配置、日志或运行命令作为证据。

代码是证据，叙述按行为路径组织，不按文件目录罗列。能驱动的事实自己查，无法确认的部分明确标为未知。理解已足以支持用户下一步时停止，不把说明扩成无边界审计。

需要跨会话保存且会影响后续判断的外部观察，按 [memory-direction](memory-direction.md) 写入 Memory；一次性的路径说明留在当前回答或当前 work。

## 审查范围

用户给出 diff、文件、目录、分支、PR 或刚改的那一批时，在该范围内审查。范围不清时先问一句；询问前可以查代码确认实际边界。

审查顺序：

1. 先独立读目标、相关代码、测试和 work 约束，形成自己的判断。
2. 按归属、命名、接口深度、状态所有权、输入边界、错误处理、真实入口和兼容影响检查。
3. 再读用户提供的已有 review 或 PR 讨论，逐条判断成立、重复、与目标一致或缺少证据。
4. 额外扫三类容易在局部自洽中隐藏的问题：跨模块交互与时序、静默丢失与覆盖、默认值与兜底掩盖的失败。
5. 按严重度报告少数高信号发现。每条给现象、影响、证据、建议和验证状态；建议“可合”前先证明最关键的安全事实。

审查不把本次明确要做且范围受控的结果误报为缺陷；若改动和声明意图不一致，或作者未意识到后果，再报告差异。没有范围时不做全仓挑刺。

## 出口

先给整体结论，再按严重度列发现。说明哪些是实测、哪些是推断、哪些无法判定。用户要求修复时，把已确认的发现写入当前 work 的证明和下一动作，进入 [change](change.md)。
