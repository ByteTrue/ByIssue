# 改变

改变用于目标已经确定的设计、功能、修复、迁移、UI 和结构调整。它们共用一个当前 work 模型；差异由范围、风险和证明方式表达。

## 选择管理强度

- 小、低风险、一次能从真实入口验证的改变：直接做，不创建 work。
- 需要跨会话、多个行为路径、完整性核对或显著风险的改变：创建或继续 `byissue/work/{slug}/`。
- 目标尚未定：回到 [clarify](clarify.md)。
- 只想知道现状：回到 [understand-review](understand-review.md)。

用户明确说“快速”“小改”“别走流程”时，仍然先判断是否能一次完成。范围、行为路径或风险超过这个边界时，说明原因并建立 work；已写的代码和证据继续复用。

## 建立或继续 work

1. 按 `SKILL.md` 找到主题匹配的 `in_progress` 或 `blocked` work。只有一个候选时继续；多个候选时让用户消歧。
2. 没有候选且变化需要管理时，用 `templates/work.md` 建 `byissue/work/{slug}/index.md`。slug 用主题短语表达，不用会话编号。
3. 在第一行代码前写目标与边界、已确认的约束、行为证明表的契约列，以及 `status`、`current_unit`、`next_action`、`must_hold`、`proof_gap`。
4. 迁移、重写、移植、对齐和“所有 X”任务按 [prove](prove.md) 从事实源生成 `scope.md`。事实源、范围或用户目标变化时重新生成。

入口的 frontmatter 是当前状态的唯一来源。正文写理由、方案和证据，不另建计划、handoff 或执行状态文件。

## 实现循环

1. 从真实入口顺着触发、责任、数据、状态和结果读到足以改变判断的程度。
2. 方案按 [economy](economy.md) 选择正确责任边界；质量目标按 [quality](quality.md) 选择；UI 关系按 [ui-spec](ui-spec.md) 表达。
3. 先打通最可能推翻方案的纵向行为，再加厚。真实入口不存在时，搭最小入口并运行一次。
4. 一次只改变一个能独立验证的行为单元。改变状态的脚本先回答：第二次运行怎样、中途崩溃留下什么、重跑是否收敛。
5. 每个单元结束时更新 work 的检查点和行为证明结果。当前单元按行为切分，不按会话数量切分。
6. 用户改变目标或约束时，先更新 work；受影响的证明行回到 `未验证`，再继续实现。

bug 先沿用户给出的坏法、日志、堆栈或测试定位根因，修复后用同一入口复验。多个假设被推翻、根因不清或行为难复现时，先补可重复失败信号，再逐个验证假设。不要把局部测试、编译或文件存在当成纵向行为证明。

## 偏离与范围

小偏差可以在 work 中更新方案后继续。目标、边界、必须守住的约束或关键证明路径不成立时，暂停并回到澄清；把证据和推荐写进当前 work。

相邻发现写入当前 work 的范围说明或单独的后续建议。新增要求先进入证明表，用户确认后才成为本次改变的一部分。

## 出口

改变完成时，先更新证明表、scope（如有）和检查点，再汇报目标、观察结果、未验证项与下一动作。行为门和范围门都通过后，把 `status` 改为 `complete`。外部副作用前按 `SKILL.md` 重新读取入口。
