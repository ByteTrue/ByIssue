# 改变

改变用于目标已经确定的设计、功能、修复、迁移、UI 和结构调整。

## 选择管理强度

- 小、低风险、一次能从真实入口验证的改变：直接做，不创建 work；但仍在对话里先明确「改后应看到什么」，再用该入口验证，无文档不等于无证明。
- 需要跨会话、多个行为路径、完整性核对或显著风险的改变：创建或继续 `bywork/work/{slug}/`。
- 目标尚未定：回到 [clarify](clarify.md)。
- 只想知道现状：回到 [understand-review](understand-review.md)。

用户说“快速”“小改”“别走流程”时，先判断是否能一次完成；超出这个边界就说明原因并建立 work，已写的代码和证据继续复用。

## 建立或继续 work

1. 按 `SKILL.md` 找到主题匹配的 `in_progress` 或 `blocked` work；多个候选时让用户消歧。
2. 没有候选且变化需要管理时，用 `templates/work.md` 建 `bywork/work/{slug}/index.md`。slug 用主题短语表达。
3. 按 [prove](prove.md) 先保存用户要求和例外，再写行为证明表。
4. 迁移、重写、移植、对齐和“所有 X”任务按 [prove](prove.md) 从事实源生成 `scope.md`。

入口的 frontmatter 是当前状态的唯一来源。正文写理由、方案和证据，不另建计划、handoff 或执行状态文件。

## 实现循环

证明表是实现循环的入口。每轮只完成一条用户行为，按「选行为 → 存检查点 → 实现 → 从真实入口验证 → 回写结果」推进；回写后才选下一行。检查点的作用是让 work 始终能回答“正在证明什么、证明了什么”，批量实现后集中补写会失去这个作用。

- **选行为。** 优先最可能推翻方案的路径。核对它的原始要求、条件和例外。
- **存检查点。** 把这行写入 `current_unit`，下一个具体动作写入 `next_action`。若本次改动会触及已通过行为的共享路径，先按 [prove](prove.md) 保存受影响旧行为的基线，并把相关证明行重开为 `无法判定`。
- **实现。** 只实现当前行为及其必要分支；公共基础缺什么补什么。方案按 [economy](economy.md) 选责任边界，质量目标见 [quality](quality.md)，UI 关系见 [ui-spec](ui-spec.md)。
- **验证并回写。** 从真实入口验证，把实际覆盖范围、证据位置和结果回写本行；失败就在本单元修复并复验，尚不能验证就写清缺口。

复查中发现遗漏或缺陷，把它作为下一待办行为，重开受影响的结果后修复。

bug 先沿用户给出的坏法、日志、堆栈或测试定位根因，修复后用同一入口复验。根因不清或难复现时，先补可重复的失败信号，再逐个验证假设。局部测试、编译或文件存在不是纵向行为证明。

## 偏离与范围

小偏差可以在 work 中更新方案后继续；目标、边界或关键证明路径不成立时，暂停回到澄清，把证据和推荐写进 work。相邻发现写入范围说明或后续建议；新增要求先进入证明表，用户确认后才成为本次改变的一部分。

## 出口

改变完成时，先更新证明表、scope（如有）和检查点，再按 `SKILL.md` 的完成门逐项核对：所有证明行和范围项通过、共享路径改动有基线和同入口比较、既有测试保持原文件与原断言、外部验收无失败、`proof_gap` 恰为空，才写 `complete`；否则保留 `in_progress`/`blocked` 和具体缺口。汇报目标、观察结果、未验证项与下一动作。
