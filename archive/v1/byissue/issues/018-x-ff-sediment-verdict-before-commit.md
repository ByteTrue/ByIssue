# 沉淀候选的裁决时点绑在收尾汇报，PR 合并后才冒出待办

## 做了什么

把沉淀候选的产出锚点从「收尾」挪到「提交」：commit / push / PR 是所有裁决的终点线，候选未裁决时同轮列出请求授权，落盘随同次提交走。用户提交前没有任何裁决类信息冒头，合并后不再出现「还有事没做」。

## 改了哪些

- `skills/bi/SKILL.md`：提交表格三行对齐——直接提交场景补「沉淀候选未裁决时同轮列出」；受管理实现与「做完/修好」两行的收尾汇报改为「关闭建议与沉淀候选」。
- `skills/bi/references/close.md`：沉淀收割标题从「收尾必做」改「提交前必做」；正文写明候选产出绑定提交而非收尾汇报；收尾汇报一节改为报裁决结果。
- `skills/bi/references/do.md`：收尾与提交段补「沉淀落盘并入单次 commit」与「直接要求提交时同轮补沉淀候选」。
- `skills/bi/references/fast.md`：ff 落盘的汇报里就列候选；用户要求 commit / PR 时候选仍未裁决的，同轮补上，并写明理由（快改没有关闭动作，沉淀跟着收尾走会拖到合并后）。
- `skills/bi/scripts/check_open_issues.py`：无 gates 分支也打印沉淀契约；gates 分支输出改为「关闭建议与沉淀候选」。
- `CHANGELOG.md`：新增 1.8.2 小节。

## 怎么验证的

`python3 tools/check-skill-repository.py` 通过。事故会话（byspace 076-x-ff，时间线出自会话日志）复盘对照：新时序下，15:07 快改汇报就应列出候选；15:09 用户授权「审查后开 PR」链，同轮补候选裁决；15:56 合并、15:58 收尾时只剩报结果——三候选均「不立档」的裁决在提交前完成，无第二笔提交。

## 对 `byissue/` 的影响

已同步 spec：`byissue/spec/index.md` 的「描述句 / 祈使句」条目下补充第三种变体「祈使句绑错时点」——绑了时点但锚点选错（「在收尾汇报中列出」，用户却在合并后才说收尾），和描述句一样不触发。事故证据：close.md 的「收尾必做」把候选拖到合并后；fast.md 的 ff 同会话直接落 `-x-ff-`、无独立关闭动作，沉淀跟着关闭走就永不触发。对抗性审查（子代理）另修正：CHANGELOG 版本引用（010 修复落在 1.6.1 非 1.6.0）、时间线统一、契约名统一为「提交契约」、「合并」纳入动作列表、快改通道补「暂不处理」出口。
