# 关闭改名会打断所有指向它的全名引用

## 预期与实际

**预期：** 按 `byissue/decisions/005-accept-number-collisions-require-full-name-references.md`，引用事项一律写完整文件名；这样即使编号碰撞，引用也永远指得准。

**实际：** 关闭事项要把路径里的 `-o-` 改成 `-x-` 或 `-d-`，于是**每一条指向它的全名引用当场失效**。今天关闭 `001`/`002`/`003`/`005`/`007` 之后，本仓库立刻产生了 4 条悬挂引用，而且是在同一天内、由同一个人、在刚写完那条规则之后造出来的。

**最小场景：** 写一条 `byissue/issues/{NNN}-o-{名称}.md` 的引用 → 关闭该事项 → 引用指向不存在的路径。

（顺带：checker 刚刚就是在这一行拦下了我写的示例路径。占位符必须用 `{NNN}` 这种既有写法，示例才不会被当成真引用——这本身算它的一个可用性验证。）

## 根因

两条契约互相拉扯，谁也没让步：

- **状态由路径表达**（`-o-` / `-x-` / `-d-`）——关闭即改名。
- **引用必须给完整文件名**——完整文件名里含状态字母。

两条单独看都成立，合起来就是「每次关闭都会制造悬挂引用」。此前没人发现，是因为**没有任何东西检查过 `byissue/` 内部的引用**。

## 已做的一半

`tools/check-skill-repository.py` 加了 `check_byissue_references`：扫全仓 markdown 里形如 `byissue/{issues,epics,notes,talks,decisions}/....md` 的引用，指不到就报 `dangling reference`。负向测试通过；跨仓引用（`pi-package-mono/byissue/...`）靠负向环视排除，不误报。4 条悬挂已修。

这只解决了本仓库。**checker 不随技能分发，用户项目里没有它。**

## 待定：产品侧怎么办

四个方向，都要权衡：

1. **`close.md` 增加义务**：改名后必须搜索并更新指向它的引用，写成强制枚举（「找到 N 处引用，已更新」）而不是描述句。便宜，但依赖每次都执行——今天反复证明了描述性义务不触发，强制枚举才有效。
2. **引用时省略状态字母**：`issues/007-description-...`——不是真实路径，不可点击、不可校验，等于放弃了全名引用的一半价值。
3. **关闭不改名**，状态回到 frontmatter——推翻 1.1.0 的路径状态设计，代价最大。
4. **接受悬挂**，只在 ByIssue 自己的仓库用 checker 兜——对用户项目等于没解决。

倾向 1，但要连带回答：跨仓库引用（用户在代码注释或别的仓库里引用事项）无论如何都兜不住，规则要不要限定在 `byissue/` 内部。

## 来源

这条是路由评测场景 ④ 附带发现的——那个子 agent 自己写了一个悬挂引用扫描器去核对 `003` 的落实情况。它没被要求这么做。见 `byissue/issues/004-x-posture-routing-regression-tests.md`。

## 实测：问题真实存在，但比想象中便宜

把 checker 的扫描逻辑跑到四个真实仓库上：

| 仓库 | 全名引用 | 悬挂 | 比例 |
|---|---|---|---|
| AGCopilot | 66 | 0 | 0% |
| byspace | 16 | 1 | 6% |
| pi-package-mono | 190 | 4 | 2% |
| toolbelt | 1 | 0 | — |
| **合计** | **273** | **5** | **~2%** |

两个结论改变了方向选择：

**1. 只有指向「仍开着的事项」的引用会断。** pi-package-mono 的三个样本全是 `-o-` 引用（`044-o-ff-ask-user-rpc-ui`、`071-o-background-terminal-bash-waitseconds`、`088-o-subagent-pure-background`），事项后来关了。而 AGCopilot 有 168 个事项、66 条引用、**零悬挂**——因为它的引用绝大多数指向已关闭事项，那些路径永远不会再变。**指向 `-x-` 的引用是永久稳定的，只有 `-o-` 是易碎的。**

（byspace 那条是例外：`020-...` 里引用 `018-` 同名文件，是编号写错，不是关闭改名造成的。）

**2. 所以选项 1 比看上去便宜得多。** 关闭时的义务不是「搜索所有引用」这种模糊负担，而是一条具体动作：`grep -r "{NNN}-o-"`，真实仓库里通常返回 0 条。本仓库今天出现 4 条，是因为这五个事项是同一天写的、互相引用密集——那是新工作区的暂态，不是常态。

**因此倾向确定为选项 1**，并写成可执行的强制枚举：

> 关闭改名前先 `grep` 一次 `{NNN}-o-{名称}`，在收尾汇报里报「找到 N 处引用，已更新」或「0 处」。

跨仓库引用仍然兜不住，规则限定在本项目 `byissue/` 与代码注释内。

## 关闭结论

按选项 1 落地：`close.md` 的关闭步骤新增强制动作——**改名前 `grep -r "{NNN}-o-"`，更新命中处，并在收尾汇报里报「找到 N 处引用，已更新」或「0 处」**。收尾汇报清单同步加入这一项。写成祈使句而非描述句，因为今天已经反复证明描述性义务不触发。

选项 2（省略状态字母）放弃：不是真实路径，不可点击也不可校验。选项 3（关闭不改名）放弃：推翻 1.1.0 的路径状态设计，代价远大于收益。选项 4（只靠 checker）放弃：checker 不随技能分发。

**为什么选项 1 便宜**，见本 issue 的实测一节：273 条全名引用里只有 5 条悬挂，且只有指向**仍开着**的事项的引用会断——AGCopilot 有 168 个事项、66 条引用、零悬挂。关闭时的动作是一次 `grep`，成熟仓库通常返回 0 条。

**验证：** 本次同时关闭 `004` 与 `008`，按新规则先 grep 出 6 处引用并全部更新；`check_byissue_references` 通过。这条规则的第一次执行就是它自己。

**毕业回写：** ByIssue 仓库侧由 `check_byissue_references` 守门；用户项目侧由 `close.md` 的义务承担。

**遗留：** 跨仓库引用无论如何兜不住，规则已明确限定在本项目 `byissue/` 与代码注释内。
