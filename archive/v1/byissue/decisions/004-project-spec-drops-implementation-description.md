# Project Spec 不再描述实现，毕业改为筛选而非搬运

Project Spec 只保留代码里重建不出来的东西：统一语言、边界与被排除的方案、长期质量约束、做/不做。能力如何运作、架构地图、数据流叙述一律不写，让代码承载。相应地，Epic 关闭时的毕业不再是「把稳定结论的具体内容合并进 Project Spec」，而是**从结论里筛出代码里没有的那部分**——多数 Epic 关闭时该进 spec 的可能只有几个词和一两条边界。

理由是 Project Spec 结构性必腐：它描述**已经存在**的东西，天生就是代码的第二份表述；而 Epic Spec 描述**还不存在**的东西，代码里没有对应物，所以不腐。这不是写得好不好的问题，是层的定义决定的。另一半理由是腐化风险与可重建性正相关——该删的恰好是既易腐化又易重建的那批，所以这刀不是权衡。

真实备选是保留「索引与命名」一层，理由是不知道能力叫什么时读代码是指数搜索。按项目实际体感否掉：让 agent 直接去找花的时间并不多。代价是 agent 冷启动更贵，接受——贵不等于错，腐化等于错。

## 背景

讨论过程见 `byissue/talks/001-what-to-build-next-and-does-documentation-rot.md` 第 4–5 节。当天的直接证据：ByIssue 自己的文档在一天内漂了四次，全部是「文档在描述系统自己已经知道的事」。存量 spec（三个仓库约 1400 行）不批量重写，随下次 close 回写时逐节收敛。
