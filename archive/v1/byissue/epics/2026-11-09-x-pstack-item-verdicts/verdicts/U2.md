## 候选汇总

### C1 非平凡批量工作先造杠杆（来自 `principle-build-the-lever`，补 `principle-build-the-lever` 缺的那块）

- pstack 原句：「When the work isn't trivial, build the tool that does it instead of doing it by hand.」「Do the first unit by hand to learn the recipe, then build the tool. Prove it by rerunning it on that unit and diffing against your hand-done version.」「For a comparison tool, seed one known-bad change for each output it claims to compare, and confirm the tool reports each mismatch.」
- bi 缺口：`references/economy.md:78` 只在「同一行为被复制到生成文件、多宿主适配器或文档副本」时要求确定性生成与一致性检查。一次扫过几十个文件做同类编辑、迁移、成批改名、跨文件分析，bi 没有任何一句让 agent 先造脚本；`references/large.md` 只要求从旧实现机械列出台账，没要求改也用机械方式做。
- 落点：`references/do.md`「实现与验证」节，一句「同类改动要落到三个以上文件时，先手工做第一个单元，再把它写成脚本并用第一个单元回跑对拍」；对比类工具再补一句「给每个声称能比对的输出各埋一个已知坏样例，确认它会报不匹配」。
- 为什么是模型的真实默认：模型倾向逐个文件手改或派几个子代理各改一摊，两者都无法被复核；`tools/` 里已有的检查脚本说明「deterministic lever」在本仓库是既有做法，只是没写进分发技能。

### C2 数字类结论的证据（来自 `principle-explain-the-number`，补 `principle-explain-the-number` 缺的那块）

- pstack 原句：「**Write the decision before you run.** Name the result that would change a decision, and the noise floor.」「**Ask "why not double?"** Name the resource or code path that bounds the result… If you cannot say why the number is not twice as good, you do not know what you measured.」「**List what else the number could be measuring, and rule out each one with evidence.**」「Keep the evidence with the number.」
- bi 缺口：`references/economy.md:96` 只挡「没有对照基线就声称节省」；`SKILL.md:18` 只要求标明实测/推断。性能、耗时、吞吐、包体积这类数字，跑之前写下它会改变哪个决定、跑完说出限制因素、排掉「测的是缓存/没跑到那段代码」，bi 一句都没有。
- 落点：`references/quality.md`「设计逐项响应，执行逐项举证」之后加一段，讲数字类证据要带跑次、离散度与被点名的限制因素；先写决定再跑。
- 为什么是模型的真实默认：模型跑一次基准就报「快了 3 倍」，不写基线、不写跑次、也不说被什么限制；这正是上一轮 talk 第 6 节记下的「推断说成实测」的同族行为，只是发生在数字上。

### C3 用数据形状承载领域（来自 `principle-model-the-domain` + `principle-foundational-thinking` + `principle-type-system-discipline` 缺的同一块）

- pstack 原句：「Encode the real domain in a data structure instead of scattering it across conditionals. A structure that matches the domain makes invalid states unrepresentable and deletes branches.」「**Data structures first.** Get the data shape right before writing logic.」「**External data is untyped until parsed.**… Have a parse function at every boundary that turns unstructured input into the typed model.」
- bi 缺口：`references/code-design.md:32`「结构跟着业务形状走」的判据是模块归属与变化轴（新变化轴 / 容器对不上 / 改一处牵一片），`references/code-design.md:88` 只说「输入边界要有归属」，都没说「这个状态该用状态机而不是两个布尔」「外部数据在边界解析成领域类型，之后别处信任类型」。
- 落点：`references/code-design.md:32`「结构跟着业务形状走」的信号表加一条：新功能给现有 if/else 加一个分支，或新增一个必须与已有布尔保持同步的布尔，说明数据形状没承载领域，先改形状；`references/code-design.md:88` 的输入边界那条加一句「外部数据在边界解析成领域类型，内部不再重复判空」。
- 为什么是模型的真实默认：模型最省事的改法就是加一个 `else if` 或第二个 `isX`，且习惯把 JSON / 命令行参数原地往下传、到处 `if not x` 兜一遍——这两件在 `references/economy.md:85`（交付前删可信路径上的判空）里已被当成要删的东西，只是没给「那该改成什么」。

### C4 会改状态的操作要可重跑（来自 `principle-make-operations-idempotent`，补缺的那块）

- pstack 原句：「Every state-mutating operation should answer: "What happens if this runs twice? What happens if the previous run crashed halfway?"」「Anything a run leaves behind, such as a lock, a temporary file, a half-written record, or a claimed job, must be recognizable as stale by the next run.」
- bi 缺口：`references/code-design.md:88` 把「重复提交、幂等」列成要在边界决定的事，`references/quality.md:50` 给了写法例子，但没有任何一句让 agent 在设计命令、迁移脚本、生命周期步骤时回答「跑两次 / 中途崩 / 收敛」并让遗留物可判过期。
- 落点：`references/code-design.md:88`「输入边界要有归属」那组加一条，或在 `references/economy.md:76`（涉及迁移、数据丢失风险时不能省反馈回路）旁边。写入形式按 `references/writing.md` 的句子写法，别用箭头。
- 为什么是模型的真实默认：模型写的脚本默认「世界是干净的、只跑一次」——直接追加写文件、先建目录再写入、失败后重跑就多一份记录；改完的迁移脚本通常没有重跑验证。

### C5 迁移期间的可破坏窗口（来自 `principle-outcome-oriented-execution`，补缺的那块）

- pstack 原句：「Intermediate breakage is acceptable when it is planned, scoped, and reversible.」「Declare where temporary breakage is acceptable.」「Require full static and runtime verification at plan completion.」
- bi 缺口：`references/code-design.md:64` 管「只留一种，迁走调用方」，`references/economy.md:44` 管「兼容策略要有今天的证据」，但没说多阶段迁移里哪一段允许暂时不兼容、由谁声明、完成时按什么全量验证。默认结果是模型给旧路径加一层 `_legacy` 别名求稳，或反过来把中间态当稳定契约写进 spec。
- 落点：`references/economy.md`「不为想象中的未来付费」节末加两三句：计划内迁移要写明允许暂时破坏的范围与恢复方式，完成时对本轮触及的区域跑全量检查。声明本身进 Epic spec 的「已定方案与必须守住」，不新建实体。
- 为什么是模型的真实默认：模型在迁移里几乎总留一层向后兼容的壳（别名、默认参数、双写），因为「不要打破现有调用」是它最强的默认之一；代价是永久多一条路径。

### C6 一条测试值不值的两条判据（来自 `principle-test-behavior-not-implementation`，补缺的那块）

- pstack 原句：「**Break the behavior.**… If the test still passes, it proves nothing. The usual causes are an assertion looser than the contract, an expected value computed by the code under test, a restated constant or prompt string that never runs the code that reads it.」「**Change the internals.**… If the test now fails, it is pinned to the implementation.」「Derive the expected value from the requirement, not from a run of the code.」
- bi 缺口：`references/code-design.md:82` 只说「断言可观察结果，而不是内部状态」，`references/economy.md:74` 只说「留下会在该行为再次损坏时失败的检查」。缺的是一个当场能做的检验，以及「期望值不能由被测代码算出来」这条最常见的错法。
- 落点：`references/code-design.md`「接口就是测试面」节，在「替换，别叠加」后加两条：把行为改坏必须红、只改内部必须绿；期望值从需求写死，不从跑一遍的结果抄。
- 为什么是模型的真实默认：模型写测试最常做两件事——用被测函数算期望值、断言 mock 被调用了几次。前者让测试永绿，后者让测试钉住实现，两者都通过「看起来有测试」的检查。

### C7 新增之前先减（来自 `principle-subtract-before-you-add`，补缺的那块）

- pstack 原句：「**Sequence removal before construction**」「When a reference has no novel content, delete it rather than leaving a stub.」「No speculative validators, parsers, or guards beyond what the spec demands.」
- bi 缺口：`references/economy.md:25` 问的是「能不能不加就达成目标」；当这次确实要加时，bi 没有一句要求在动手前先把同一块里的死代码、冗余校验、无内容占位删掉，于是删的动作只发生在自己新加的 diff 上（`references/economy.md:82`）。
- 落点：`references/economy.md`「从不新增开始」节末加一句顺序：确定要新增后，先删掉这块已死或不成立的部分，再在新基础上写。
- 为什么是模型的真实默认：模型几乎从不删存量代码，只会绕开它或并存；`references/code-design.md:64` 的「两种做法只留一种」说明本仓库已经在别处对付同一后果，只是没给「先减后加」这个顺序。
