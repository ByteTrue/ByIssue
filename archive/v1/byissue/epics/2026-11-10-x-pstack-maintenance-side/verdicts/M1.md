## 候选汇总

### C1 一句话改动的行为对照记录（两臂同结果就删，未验证的路径单列）

- **做什么**：改 `skills/bi/` 里任何一条会改变动作的句子后，用同一个低价模型跑两臂（旧文本 / 新文本 × 同一场景），记下模型名、次数、两臂的工具调用序列和产物差异；两臂行为相同就**删掉这句话**，不因为「看起来更保险」留着；跑不到生效路径的项单列成「未验证」，不要写进「已通过」。
- **挡什么**：A 族「写了但不执行」与否定式的无限增长。`tools/retro-failure-modes.md` 第二节把 A 族记成 4 条，A+B+C 合计 10 条、占 48%，并写明复发链 001→008→011→018；每次修法都是改措辞，而「这条措辞有没有改变模型动作」从来没被对照过。
- **证据**：pstack `CHANGES.md:59`（0.9.128）在 10 个真实会话里分三臂对照，行为完全相同，于是删句：「Live sessions with `pi-subagents` 0.84.0 installed beside pstack showed that it changed nothing … In all 10, the model read `pi-tools.md`, called `subagents_enable` and then `subagent`, and never called `agent`」；同文件 `:205`（0.9.106）记了反面：「The previous prompt also kept it in that run … so the run does not tell the two prompts apart」。ByIssue 已经做过一次并写进 `CHANGELOG.md:45`（「Two more were removed after A/B runs … 5/5 note-posture runs without it still wrote flat `notes/YYYY-MM-DD-name.md`」），但这条判据只停在 changelog 的叙述里。
- **零依赖做法**：纯 Markdown 加一节判据，跑测试仍用现成的 `tools/fixtures/posture_table.py` + `tools/fixtures/posture_judge.py`，不写新脚本（判据已在 `tools/posture-scenarios.md`：`:19` 两臂同一模型、`:20` 先确认被测文件在这条路径上会被加载、`:24` 判据是调用序列）。
- **落点**：`tools/posture-scenarios.md`「怎么跑」加一条判据（两臂同结果 ⇒ 删句，并把模型/次数/未验证项写进 CHANGELOG 该版一行）；不改 `skills/bi/`，所以不动 `VERSION`。
- **成本**：每条句子 2 臂 × 3 次子代理，约 20–40 分钟墙钟；不需要跑全表。真正的成本是它会把「加一条规则」变成「先证明这条规则有作用」，这会减少新增条款的数量。

### C2 CHANGELOG 版本闸门（最新小节必须是 VERSION，同一版本号不得两节）

- **做什么**：pstack 的发布闸门要求 `CHANGES.md` 的第一个版本标题就是 `VERSION` 那个版本，并拒绝一个版本号出现两个小节（`CHANGES.md:447`：「requires the first version-led heading in `CHANGES.md` to be the `VERSION` heading and rejects a version that heads two entries, so an entry without a bump fails CI instead of shipping an inert release」；围栏里的标题不算）。
- **挡什么**：版本号与小节脱节的两种残余形态——小节写在新位置但顺序乱了、同一版本号两节（一次 bump 写重）。ByIssue 现在只判「出现过」：`tools/check-skill-repository.py:35` 的 `check_version`，唯一失败句是 `:46`「missing version section」。**拿不准**：ByIssue 历史上是否真发生过同号两节，我只能看到当前 `CHANGELOG.md` 是 28 节、降序、无重复，没有查 git 历史（只读且未跑 `git log -p`）。所以这条是预防性候选，优先级低于 C1。
- **证据**：上面 pstack 的行；ByIssue 侧的缺口就是 `check_version` 那十行实现本身。
- **零依赖做法**：`check_version` 里加约 10 行：按 `^## (\d+\.\d+\.\d+)` 取标题列表（跳过 ``` 围栏），断言第一项等于 `VERSION`、集合无重复。`tools/check-skill-repository-selftest.py` 加两个坏夹具（同号两节；首节不是 VERSION），跑一次自测证明会红。
- **落点**：`tools/check-skill-repository.py` + `tools/check-skill-repository-selftest.py`；不需要改 `skills/bi/`。
- **成本**：半小时以内，之后每次发布零额外动作。

## 附：pstack 的变更记录写法（格式观察，供父会话核对）

- **文件头先声明它是哪种文件，并把别的账本指出去**：`CHANGES.md:3`「This file is the release changelog, with one `## <version> - <title>` entry per release, newest first. The Cursor-to-Claude rewrite rules live in [`tools/substitutions.json`](tools/substitutions.json), and the [sync boundary](CONTRIBUTING.md#the-sync-boundary) … defines how a change to upstream's skill content is declared」。ByIssue 的 `CHANGELOG.md` 没有这句，也没有「别的账本在哪」的指针（读者要自己摸到 `byissue/decisions/`）。
- **标题写用户可见的行为，不写内部编号**：0.9.133「worktree audit ref and PR fixes, setup-pstack runtime notes」、0.9.128「credential-forward shapes removed, pi agent tools: off without the prompt sentence」。ByIssue 只有 `## 1.14.1`。
- **每段固定顺序：原来的行为错在哪 → 新行为 → 为什么 → 谁发现**，例：`:15`（0.9.132 的 fence 模式漏 CRLF）、`:191`（0.9.108 缺一次自重启，于是更新后第一次调用就失败）。
- **「**Verified.**」是独立一段，带环境、版本、通过数、失败数**：`:169`、`:251`、`:269`、`:279`、`:729`。没有验的部分在同一段末尾点名（`:85`「No live MiniMax session has run … so the hook, skill loading, and agent dispatch inside a session are untested」）。
- **维护动作本身也有数字**：`:235`「Measured with `bun tools/sync.mjs e73df47`: 83 files unchanged, 38 excluded, 4 updated, 28 added, 5 merged, and 6 conflicts」。ByIssue 侧的同类数字只出现在叙事里（`CHANGELOG.md:24`「41 runs; three failures」）。
- **不做的也说**：`:89` 0.9.124 说清检查会因此变严（「a plan written from an earlier skeleton fails the check until that line is updated」）；0.9.94/0.9.19 有整段「Deliberately not ported」。ByIssue 用 `byissue/spec/index.md`「当前没有的东西」承担这一职能，位置不同但功能在。
