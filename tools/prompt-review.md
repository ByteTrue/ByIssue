# 技能文本审查

`skills/bi/` 是散文即逻辑。改一条规则就可能改变 Agent 的行动路径。发布前对整个技能包做一次独立阅读，检查新增文字是否改变判断，是否与现有契约冲突。

## 审查顺序

1. 先读 `skills/bi/SKILL.md`，列出四种行动、work 检查点、行为门、范围门和 Memory 边界。
2. 逐篇读核心 reference，确认每条规则只有一个归属，引用文件只补充它自己的增量。
3. 核对所有路径、模板和初始化脚本。用户安装后只能看到 `skills/bi/`，包内不能引用仓库根的 `tools/`、`byissue/` 或 `CHANGELOG.md`。
4. 选择一个澄清、改变、理解与审查、记忆与方向的真实场景，沿入口读到结果，检查规则是否给出下一步动作。
5. 对每条完成声明追问行为证据是否走到真实入口；对迁移、重写、移植和“所有 X”追问是否另有范围覆盖。
6. 对照 `diff` 删除只增加阅读量、不改变决策的句子。规则要写当前契约，演变原因写历史记录。

## 发现的写法

每条发现给出文件、原文、具体场景、错误动作和最小修法。无法由静态阅读判断的行为标为“无法判定”，说明需要在真实项目中观察什么。修法落地后重新读相关入口并运行 `bash tools/release-check.sh --no-deploy`。

重点检查：

- 用户改变目标后，work 检查点是否会被更新，受影响的证明是否回到未验证。
- 从压缩摘要继续时，下一动作是否来自 `next_action`，而不是来自摘要里的自述。
- “完成”是否同时要求行为门和范围门。
- Memory 是否只记录未来需要的内容，是否把代码能回答的事实复制成第二份真相。
- 模板和脚本是否会把技能包专属路径写进用户项目。
