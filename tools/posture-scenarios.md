# 姿态路由场景表

`bi` 的行为链是「读用户这句话 → 选一个姿态 → 只读那个姿态的必读 → 按那套规则做事」。选错姿态，后面全错。这张表是那条链的期望值。

## 怎么跑

**主跑法：直接用 subagent，不要写脚本。** 执行这份表的是 agent，不是 shell——手上有 subagent 工具就直接用它，别把自己降级成只会调 `python3` 的执行器。

每条场景起一个子 agent，并行开：

- **`cwd` 指向一份可写的临时副本**：`rsync -a --exclude .git ./ /tmp/bi-eval/`。子 agent 必须能真的动手，否则行为会变形——首次评测用只读工具，结果第一条直接回「我改不了文件」就收工，那条数据作废。
- **fixture 必须含有该场景要操作的东西。** 拿本仓库当 fixture 只对「读哪些文件」这类路由断言有效；一旦场景要动手改产物就不会有判别力。实测三种失败形态，都是 fixture 缺目标物、不是路由错，观测作废：说「把这个 epic 关了吧」→「这里没有 epic」（本仓库 `epics/` 为空）；说「顺手把这个也改了吧」→「『这个』没有指代对象」；说「顺手改一下这个 README 里的错别字」→ 路由对了、也读了 `fast.md`，但仓库里并没有错别字，于是把 16 轮全烧在通读两个 README 上（这条只证明了触发词有效，场景断言拿不到）。要测关闭就造含 `{日期}-o-{Epic名}/` 的副本，要测受管理实现就造仍 `-o-` 的 issue，要测改文案就在 fixture 里放一处真的错别字。**先问一句「这个场景期望子 agent 改哪个文件」，答不上来就换 fixture。**
- **要测动作路径，fixture 得让条件真的成立。** 实测一个只有 Epic 目录、子 issue 仍 `-o-`、没有代码的副本 + 「关闭条件满足了，关掉它」：子 agent 正确拒绝关闭（要求证据），于是那条只验证了「会读 `close.md` 并守住关闭门槛」，**没验到改名与修引用的路径**。把同一句话换成子 issue 已关、有验证记录的副本，子 agent 就走完了动作路径：改名前 grep 到 2 处引用 → 更新到新路径 → 改名目录 → 改后再 grep 确认 0 处，并在收尾汇报里报了「找到 2 处引用，已更新」。拒绝路径和动作路径是两条不同的断言，别指望一个 fixture 同时测到。
- **依赖前文的场景必须补上上下文。** 「顺手把这个也改了吧」的 `这个`、「继续 talk」都必须有指代对象，否则子 agent 只会（正确地）追问指代对象，你无法区分「追问得对」与「路由失败」。要么在 `task` 里补一两轮前文，要么改用不依赖前文的说法（如「顺手改一下这个 README 里的错别字」）。
- **夹具要搭在它将要运行的环境里。** 契约里写的命令会在真实项目里跑，真实项目默认是 git 仓库、有依赖与构建产物目录；夹具若只是一个光秃秃的临时目录，就验不出那些形态。实测：修引用契约的 `grep` 命令在无代码目录里验了六轮都对，第七轮拿到真 git 仓库一跑，`.git/COMMIT_EDITMSG` 与二进制的 `index` 就混进了命中——那是永远清不干净的残留。命令涉及文件系统遍历的，夹具至少要有 `.git` 与一个噪声目录。
- **给完整工具，不要限制为只读。** 副本提供隔离，工具限制只会污染观测。
- **`maxTurns` 至少 15。** 首次用 8，三条被截断在关键处。
- `task` **只放那一句话**，不要附加「请说明你进入了哪个姿态」——那会污染路由。
- 跑完读子会话日志，看它**实际读了哪些文件**，与本表比对。判据是调用序列，不是它自己的说法。

**注意技能来源：** 子 agent 加载的是部署副本 `~/.agents/skills/bi/`，不是仓库里的 `skills/bi/`。改完必须先 rsync 同步再跑，否则测的是旧版本。

为什么必须是子 agent 而不是你自己：上下文隔离。已经参与过设计讨论的 agent 知道答案，测自己等于自己判自己。

**「不应读取」比「应读取」更能暴露问题**：多读一个文件意味着路由没收敛，正是这个技能要避免的。

**结构体检（附带）：** `python3 tools/check-skill-repository.py` 会校验姿态表没坏、触发词不被两个姿态同时占用、每个姿态都有场景覆盖。它**不验证语义路由**，只是棘轮——新增姿态时不补场景就红。

改过 `SKILL.md` 姿态表或任一必读文件后，两个都跑一遍。

## 状态字母读法探针

姿态路由之外还有一层会被路径编码吃掉：**状态字母本身读得对不对**。字母没有消歧信息，模型只能拿先验补全——`d` 在这个位置被读成 draft 是真实事故，换成 `w` 之后竞争先验变成 `wip`（in progress），那是更糟的错读：已放弃的事项被当成活跃事项。

夹具 `tools/fixtures/state-letter-probe.sh` 一次搭四臂，判据是子 agent 报出的状态而非它的推理：

| 臂 | 目录 | 断言 |
|---|---|---|
| `w-clean` | `2026-09-09-w-client-plugin/`，无子 issue | 读成放弃 / 不做 / won't do；不得出现进行中、还没做完、在做 |
| `w-settled` | 同上，内部一个 `-x-` 子 issue | 同上；已关的子 issue 不改变 Epic 状态 |
| `w-violation` | 同上，内部一个 `-o-` 子 issue | 仍读成放弃，**并且**指出这违反 `close.md` 的关闭前置条件（关闭 epic 要求内部事项已关或明确废弃/移出）；不得把 Epic 读成进行中 |
| `o-control` | `2026-09-09-o-client-plugin/` | 读成进行中 / 开着；不得出现放弃 |
| `x-control` | `2026-09-09-x-client-plugin/` | 读成已交付 / 关闭；不得出现进行中 |

两个 control 臂排除「一律答放弃」与「字母被整体忽略」两种假通过；`w-violation` 排除「死按字母、看不见契约违反」。每条场景只问一句「这个 epic 现在什么状态？」，`task` 不加别的话。

搭 `w-settled` 时先读 `close.md`「关闭 epic」：它要求内部事项已关或明确废弃/移出，所以「Epic 已 `-w-` 但子 issue 仍 `-o-`」是契约不允许的状态，只能放在 `w-violation` 臂里当反向断言用。
