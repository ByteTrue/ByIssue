### Go 移植“零遗漏”结论的复核

这条需要从“后续发现漏项”升级为可复核的反例：

- 提交 `4f93ce184` 的 Epic spec 写着 `MISSING 0 · 已实现未接线 0`。
- 同一提交中，`internal/server/server.go` 的 `tunnelsEnabled` 只有测试赋值；生产初始化没有从配置读取，零值使 gate 保持 `false`。
- `internal/tunnel/registry.go` 有 `Registry.Start()`，但提交内没有生产调用；`internal/server/tunnels.go` 只在首次 RPC 时创建 registry 并调用 `SetEnabled(false)`。
- 后续提交 `24a7b83de` 的提交说明明确写出四个死链：gate 未赋值、`Registry.Start` 未调用、生产 peer transport 未接线、stream protocol 不能打开流；并补了 `ApplyTunnelConfig` 与 gate 测试。

因此，这不是单纯的“某条 Node 文件没有对应 Go 文件”。当时的账本检查确实通过了文件覆盖、结论计数和字段对账，但没有验证“配置 → 启动 → transport → 用户可观察行为”的纵向链路。`已实现未接线 0` 还是一个由账本作者写出的结论，不是从运行入口机械得出的事实。

## 外部材料提炼

### 代码/运行事实

- pstack：`how` 解释当前代码，`why` 调查动机；要求代码作为机制证据，不作为意图证据；“single source of truth”优先于同步副本。
- pi 作者访谈：反对把自然语言 spec 无限写细，空白仍要由模型补全；架构边界和模块大小需要有经验的人先想清楚。

适用边界：代码、测试、运行结果能重建的内容不进入 bi 的第二份事实库；需求、取舍、外部限制仍需要独立记录。

### DSH / write-notes-like-deepseek

- docs 记录当前事实，notes 记录为什么、放弃了什么。
- 只有代码、测试和现有文档不能解释的长期理由才值得留 note。
- 新决定必须说明真实备选及其最强理由；决定翻转开新记录，事实变化可以原地同步。
- 格式、生命周期、归档封印可以机械校验，但校验不证明 Agent 真的遵守决定。

适用边界：借“理由/备选/代价”这个内容模型，不照搬四种生命周期、六种分类、强制每次非平凡变更留 note。

### Matt

- 有效范式：澄清问题→形成可执行 spec/计划→实现→review→retro；`grill` 通过提问暴露未决问题。
- 适用边界：需求含糊或方案未定时有价值；清晰小改不应完整走一遍。

### OpenSpec

- 有效范式：稳定真相与正在发生的 change 分离；change 可在执行中修正。
- 适用边界：变化跨度大、需要跨会话接续时；不把 artifact 状态机和详细 spec 作为所有任务的默认路径。

### pstack

- 有效范式：入口路由、how/why 分离、结论带证据、可运行问题自己验证、反复错误变成检查。
- 适用边界：调查、架构判断、验证方法；不把其完整 playbook 数量和 PR 流程移植进 bi。用户已有真实使用结论：pstack 不能直接成为 bi v2 的底座。

## 当前暂定要求（不是实现方案）

1. bi 不再维护代码可推导出的“当前系统副本”。
2. 每项非平凡变化只需要一处当前工作记录，记录原始目标、已定取舍、范围、当前状态和证据；小改可不落盘。
3. 长任务的范围必须能从事实源重新列举；Agent 自己写出的清单不能成为唯一完成依据。
4. 每个工作单元必须有可观察的完成证据；“写了记录/提交存在/测试相邻通过”不等于完成。
5. 记录只留下代码无法还原的意图、边界、外部事实、放弃方案和重访条件。
6. 规则只保留一个归属和一个执行时点；不在多个 reference 中重复同一契约。
7. 开始和接续都先输出一份短的“当前工作摘要”，内容必须指向当前变化，而非复述整个项目。
8. 完成前重新从原始范围/事实源列举一次，并报告遗漏、未验证和偏离；不能仅复述自己的计划。
9. 普通小改按价值留档；Vision/产品全景按需保留，但不进入普通改变路径。

## 明确排除

- 不把 harness hook、自动压缩注入、插件实现等作为 bi 方案。
- 不把完整 OpenSpec/Matt/Superpowers/pstack 流程拼接成“大一统生命周期”。
- 不以“文档更多”作为可靠性指标。

## 目前能下的判断

### bi 已经证明有价值的部分

- 把调查从猜测推进到“触发 → 责任边界 → 可观察结果”，并要求行为验证；AGCopilot 锁死 bug 的变异测试、review 和 CI 结果是正例。
- 让需求变化进入当前工作，而不是把最初 spec 当成不可修改的预言；AGCopilot 问卷的真实 UI 迭代是正例。
- 在大任务中从事实源列举范围、用固定结论推进、完成前重新列举，确实能减少“自己拆的清单漏掉原始范围”；Go 移植第二轮的账本修订过程证明它能抓住文件级遗漏。

### bi 尚未解决的部分

- **纵向可用性**：文件覆盖和字段对账不能证明配置、启动、传输、用户行为之间的链路接通。隧道案例中，账本正确但功能完全死掉。
- **记录可信度**：Epic/spec 可以写出“已交付”和“零遗漏”，却仍然是 Agent 生成的声明；它不能替代从运行入口和真实路径重新验证。
- **跨会话执行**：记录存在并不等于接续 Agent 找到、读懂并遵守；当前样本还没有证明多单元、多会话长期推进可靠。
- **压缩后的边界保持**：短探针证明过“摘要接续时重读”这条规则，不足以证明真实长任务经过多次压缩后仍不漂移。

### 新设计必须满足的硬要求（仍不是目录方案）

1. 范围覆盖与行为可用性必须是两种不同的证据，不能由同一张源文件账本替代。
2. “完成”只能由用户目标对应的可观察路径证明；代码存在、记录存在、相邻测试通过都只是局部证据。
3. 当前变化的记录必须把原始目标、已定取舍、覆盖来源、当前接续点和证明结果放在一个显眼入口。
4. 稳定事实、当前变化和长期取舍要分开；代码能重建的实现事实不再抄进 bi。
5. 流程只在真实动作发生时触发判断，不能把“读过规则”当作“执行过规则”。

### 还不能据此断言的事

- 不能断言“删掉实体/文档一定更可靠”；目前只有对旧流程的失败证据，没有新流程的长期对照。
- 不能断言“压缩是全部根因”；隧道案例主要是范围/判据盲区，和上下文压缩无关。
- 不能断言“必须采用 changes/目录”；当前证据支持的是唯一当前变化入口，不支持具体命名。
