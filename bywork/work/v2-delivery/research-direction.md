# bi 重写候选方向（讨论稿）

更新时间：2026-11-13
状态：研究中；下列“已确认”是讨论中已拍板的设计约束，不是已实现方案

## 目前确认的问题

旧 bi 试图同时承担四件事：

1. 记录用户目标和已定取舍；
2. 管理大任务范围与拆分；
3. 证明实现真的可用；
4. 保存长期可复用知识。

它为这些职责建立了很多实体和规则，但职责之间没有清楚分开。结果是：

- 文件账本可以证明“覆盖了源文件”，却不能证明“纵向功能链路接通”；
- 记录可以存在，却不能证明接续 Agent 使用了它；
- 规则可以被读过，却不能证明它在关键动作上被执行；
- 每次工作都背上知识管理成本。

## 可能的最小内核

### 1. 目标

这次要让用户看到什么变化？有哪些明确不能改变的边界？

### 2. 范围

原始范围从哪里机械列出？哪些内容属于本次变化？哪些明确不属于？

### 3. 证明

完成时，用户可观察的哪条路径必须跑通？源文件覆盖和行为证明分别记录，互不替代。

### 4. 当前接续

当前已经决定什么、完成什么、尚缺什么、下一步从哪里开始。

### 5. 记忆

只保存代码无法重建、未来还会影响判断的目标、约束、取舍和外部事实。

这五项是职责，不是最终目录设计。普通小改可以只在对话中短暂存在；跨会话或高风险变化才需要落盘。

## 讨论中已确认的设计约束

### 不兼容旧 bi 产物

重新设计时不以旧 Issue、Epic、ff、Explore、Project Spec、Decision、Note、Tool 的形态为约束；历史材料只作为取证，不承诺迁移或兼容。

### 一个当前工作实体

所有需要跨会话、管理或完整性证明的行动统一成一个“当前工作”。讨论、设计、调查、修 bug、实现、验证是它的动作或阶段，不再各自产生不同工作实体。一次会话内的小改可以没有当前工作记录。

候选承载形状：

```text
当前工作/
├── index.md       # 唯一当前状态入口
└── scope.md       # 只有需要机械枚举范围时才有
```

`index.md` 需要显眼承载目标与边界、已定方案与约束、行为证明、当前状态和接续点；`scope.md` 只承载从事实源机械列出的范围，不承载第二份总状态。

### 四种行动模式

1. **澄清**：目标或取舍未定；查事实、问用户，不创建当前工作。
2. **改变**：目标已定；创建或继续当前工作。bug、设计、迁移、UI、重构都是改变的不同问题形态；快改是无需当前工作记录的轻量改变。
3. **理解与审查**：解释现状或按用户给定范围检查，不默认改变代码。
4. **记忆与方向**：按用户要求维护长期记忆或方向；方向不进入普通改变路径。

不再把关闭作为行动模式；不再区分“完成”和“关闭”。当前工作路径稳定，满足证据条件后直接标记完成；长期记忆另行筛选，不做毕业搬运。

### 行为证明是非平凡改变的硬前置

完成不能只凭代码存在、文件覆盖、记录存在、提交存在或相邻测试通过。每个非平凡改变都要从本次改动实际影响的真实入口走到可观察结果：入口可以是 UI、CLI、公开 API、协议或服务启动链。不同改动不要求相同层级的完整 E2E，但必须穿过本次改动的边界。

如果仓库没有可驱动真实行为的入口，先搭最小入口并跑通一次；仍然无法走通时只能标为“未验证”，不能报告为完成。

范围覆盖与行为可用是两种不同证据：迁移、重写、“所有 X”等任务可额外使用 `scope.md` 从事实源机械列举，但范围表全绿不能替代行为证明。

这条门槛约束“改变”模式的代码/产品变化；澄清、理解与审查、记忆与方向有各自的出口，不为没有运行时行为的工作虚造行为测试。

### 当前工作按条件创建

目标含糊时先澄清，不建当前工作。确认要做后，只要需要跨会话接续、多个行为路径、完整性核对或明显风险，Agent 直接创建当前工作；一次会话内的小改不建。

### Memory 统一长期记忆

把旧 spec、decision、note、tool 的长期职责收敛为 Memory 条目。只保存代码/git 无法重建且未来仍影响判断的内容，并标出依据类型：用户决定、外部观察、可重跑证明。Vision/方向按需保留，不进入普通改变路径。

记忆按证据触发，不做每次完成或提交时的固定沉淀盘点：用户长期决定、已确认的外部事实、值得复跑的检查直接写；代码可重建、一次性过程和一次性试探不写；价值不确定时带推荐让用户定。

## 长会话连续性：重点不是主动 handoff

Matt 的 `handoff` 解决的是少见的“让工作离开当前上下文”——换 harness、换目录、交给同事或分叉旁路任务。它是可携带的二级摘要，不是当前工作的真相源；它自己也承认临时文件可能消失、摘要可能把未验证判断写成事实。

这不是 bi 当前的主问题。真实失败集中在同一项工作经历多轮压缩后，契约离开了执行点：

- 六次压缩后直接 push，正确的关闭与提交时序没有在动作点重新出现；
- 大任务在压缩后虽有记录，但接续时需要重新确认方案、范围和当前单元，而不是相信摘要中的一句“继续”；
- 已有 `large.md` 的三个重读时点是正确方向，但它依赖 Agent 发现自己“正在从压缩摘要接着来”，且重读对象仍分散在 spec、台账和当前事项中。

因此新 bi 的核心不是 `handoff`，而是**当前工作检查点（checkpoint）**。这一点已确认：

1. `work/{slug}/index.md` 顶部的结构化元数据就是五项短卡：`status`、`current_unit`、`next_action`、`must_hold`、`proof_gap`；正文不重复这份状态；
2. 每个阶段性单元结束时，把已经成立的事实和证据回写入口；
3. 从压缩摘要继续、开始下一个单元、执行外部副作用或宣布完成前，先重读入口，并核对代码/git/证据；
4. 核对后若入口与现实不符，先修正当前工作快照或停下澄清，再继续；不能把摘要里的“已完成/下一步”当成事实；
5. 接续的第一件真正动作必须来自入口中的单一下一动作，而不是从上轮对话猜测。

单元按可验证行为切分，不按“一个会话”切分；会话可能经历多轮压缩，不能成为完成边界或可靠容量单位。

不维护全局 `current.md` 指针。压缩后或收到“继续”时，按用户主题与当前代码变化寻找状态为“进行中/阻塞”的工作入口；找到一个就读它，多个才询问，找不到则按小改或创建当前工作处理。这样不会让并行会话互相覆盖当前指针。

### 四个案例反向检验

| 案例 | 压缩后检查点应暴露什么 | 完成门如何挡住旧错 |
|---|---|---|
| Node → Go 移植 | 当前范围单元、范围来源与当前纵向行为单元分开显示 | `scope.md` 全部有覆盖不能替代行为路径通过；行为缺口仍保持未完成 |
| tunnel 接线 | 当前行为单元明确到“配置 → 启动 → transport → 用户可观察结果” | 文件对应物和局部测试全绿但真实路径未通过，不能标完成 |
| 六次压缩后 push | 当前卡显示剩余证明/范围缺口和提交前唯一下一动作 | 外部副作用前强制重读并核对，不依赖会话开头记忆的时序规则 |
| 满意度问卷需求变化 | 用户新增约束与当前行为契约更新在同一入口 | 新需求成为当前快照的一部分，后续不会继续按过时初始方案推进 |

这样，跨会话只是“重新进入当前工作”，不是创建一个交接状态。用户极少明确说“交接给另一个 agent”时，才按需生成 Matt 式运输简报；它只引用当前工作入口，不进入 bi 的常规结构。

## 暂不接受的推论

- 不因为“单一当前记录”听起来简洁，就立刻拍平现有实体；先证明它能承载范围、证明和接续。
- 不把代码唯一真相推成“需求、取舍和外部运行事实都不需要记录”。
- 不把文件账本升级成更大的账本来解决纵向验证问题。
- 不把 pstack、Matt、OpenSpec、DSH 的完整工件和生命周期拼接进来。

## 旧结构的初步去向

### 合并进当前工作

- Issue、Epic、ff：统一成为 `work/{slug}/`，差异改由工作规模、范围来源、行为证明和当前阶段表达。
- Explore：成为改变前的理解动作；需要跨会话时仍进入同一个 work，不另设调查实体。
- Talk：短讨论留在对话；讨论本身需要跨会话时，当前 work 的目标就是厘清这件事，不另建 Talk 记录。
- `large.md` 的台账、单元和重读：拆成 `scope.md`、行为证明、五项检查点与重新进入协议，不保留 Epic/ledger 双入口。

### 合并进 Memory

- Project Spec、Epic Spec、Decision、Note、Tool 的长期判断职责统一为 Memory 条目；具体可执行脚本仍是代码/工具产物，Memory 只保存它无法表达的边界、依据和使用条件。

### 独立保留

- Vision/方向：只在用户整理长期目标或当前工作确实受其约束时使用，不进入普通改变路径。
- 代码、测试、脚本、git 与真实运行产物：继续作为实现事实和行为证据来源，不由 bi 文档复制。

### 退场的旧配套

- 以 open/close、路径改名、毕业回写为前提的 `check_open_issues.py`、close 契约和实体模板不再属于新协议。
- 旧的 13 姿态路由、按姿态分裂的实现/收尾/快改/修 bug 文档需要收敛为四种行动模式及其按需材料。
- `init_bywork.py` 只保留新工作区的最小目录初始化，不再创建旧实体全套目录。
- 新协议只把 `work/`、`memory/`、`vision/` 视为当前工作区入口；旧目录若仍存在，作为历史材料，不自动迁移、不自动混读，也不承诺兼容。
- 新工作区按需创建 `work/` 与 `memory/`；用户明确整理方向时再创建 `vision/`。初始化只补新入口，保留旧目录原样，不做迁移或旧状态解释。

### Reference 收敛方向

主入口只负责四种行动、当前工作检查点、证明门和记录边界。旧 reference 不按原姿态一一保留，先按职责合并：

- `clarify`：讨论、grilling、术语/领域澄清；
- `change`：设计、修复、实现与结构变化的共同推进规则；
- `prove`：行为证明、scope、检查点和完成门；
- `understand-review`：现状说明与有界审查；
- `memory-direction`：Memory 与 Vision；
- `quality`、`economy`、`ui`、`writing`、`onboard`：只有场景需要时按需加载的原则材料。

具体实现前仍要逐份检查旧 reference 的有效原则，避免把旧实体的状态契约连带搬回新入口。

## 当前候选内核（供下一轮逐项挑错）

```text
bi
├── vision/                 # 可选方向；普通改变不默认读取
├── work/{slug}/
│   ├── index.md            # 当前工作的唯一权威入口与五项检查点
│   └── scope.md            # 仅在需要事实源完整性时存在
└── memory/{topic}.md       # 代码无法重建且未来仍影响判断的长期内容
```

### 四种行动

1. **澄清**：目标、术语或取舍未定；查事实、问用户、形成共识。短讨论留在对话；讨论本身需要跨会话时，建立一个以“厘清该问题”为目标的 work。
2. **改变**：目标已定；按条件创建或继续 work。设计、修 bug、功能、迁移、UI、结构调整都是问题形态，不再各自产生实体。
3. **理解与审查**：解释现状或按用户给定范围检查；默认不改代码。
4. **记忆与方向**：维护 Memory 或 Vision；不把普通改变自动升级成产品方向工作。

### 改变的最小闭环

```text
目标与边界
  → 行为证明契约（真实入口 → 操作 → 可观察结果）
  → 按行为切分当前单元
  → 实现与局部验证
  → 真实路径证明
  → 必要时范围覆盖核对
  → 更新检查点并继续或完成
```

### 当前工作的检查点协议

- 入口顶部结构化元数据就是五项短卡：状态、当前行为单元、唯一下一动作、必须守住的约束、证明缺口；正文不复制它。
- 工作单元按可验证行为切分，不按会话数量切分。
- 开始单元、单元完成、用户改变目标/约束、外部副作用前、宣布完成，以及从压缩摘要继续时，先读短卡并核对代码/git/证据。
- 入口与现实不一致时，先更新入口或停下澄清；摘要、commit 或“文件已改”不构成当前状态。
- 重新核对时分开三类真相：用户最新明确要求决定目标与边界；代码、git 和真实运行决定已经发生什么；work 记录保存已选方案、范围和证据状态。实现与记录不一致时更新进展，预期与实际不一致时保留失败/未验证，不把实际结果改写成预期。
- 当前工作完成需要行为门与范围门都通过；完成后原路径保留，不执行关闭或毕业搬运。
- 完成 work 是一项已结束变化的证据入口；新的目标或新增范围建立新的 work 并链接旧 work。若后来证据推翻完成结论，直接把原 work 的状态改回进行中/阻塞并更新证明，不设置重新打开仪式。

### 轻重边界

- 小而低风险、一次能完成的改变：证明契约留在对话，不创建 work。
- 出现跨会话、多个行为路径、完整性核对或显著风险：直接创建 work。
- 小改中途升格时，把对话中的目标、证明和已发生事实补入 work，不重做。

### 对历史失效族的对应关系

| 失效 | 新内核的对应动作 | 仍需承认的边界 |
|---|---|---|
| 规则/目标没有记录 | 改变前先写目标、边界和证明契约；用户新要求先更新 work | 只对需要 work 的变化强制落盘，小改仍留在对话 |
| 记录存在但接续没读 | 重新进入先找 work、读结构化短卡、核对现实 | 这是流程前置动作，不能靠记录存在自动发生 |
| 读了但动作仍偏离 | 行为门、范围门和外部副作用前的重读把判据绑到动作点 | 文字协议仍不能证明 Agent 诚实填写证据；证据必须来自真实入口 |
| 清单覆盖冒充功能可用 | scope 只记覆盖，行为证明单独过门 | 不能用一张更大的账本消除运行时未知 |
| 同一契约多处表述 | 当前工作入口为当前状态唯一来源；Memory 只保留长期判断 | 场景原则仍可分 reference，但同一动作契约只保留一个归属 |

## 三种最小记录契约

### `index.md` 的行为证明

行为证明使用一张同时承载契约和结果的表，不分成“计划表”和“验证报告”两份：

| 行为路径 | 真实入口 | 操作 | 应观察到 | 证据 | 结果 |
|---|---|---|---|---|---|
| ... | ... | ... | ... | 待跑 | 未验证 |

创建 work 时先写前四列；跑过后回填证据与结果。每行应足够小，一次观察能判断；局部单测、文件存在或 mock 掉被测链路只能作为辅助证据，不能单独让该行通过。

用户改变预期行为或边界时，先更新目标、范围和这张表；受影响的旧证明回到 `未验证`，原证据只保留为历史依据，不能继续证明新目标。新增要求先成为证明行，再进入实现。

### `scope.md` 的范围覆盖

`scope.md` 只回答“事实源列出的范围是否逐项处理”，不使用“完成”状态：

| 来源项 | 所属行为单元 | 覆盖状态 | 覆盖依据 |
|---|---|---|---|
| ... | ... | 未处理 | ... |

覆盖状态只取：`未处理`、`已覆盖`、`明确不做`、`不适用`。`明确不做`须有用户或已确认边界依据；`不适用`限于没有运行时行为的项并说明原因。范围表全 resolved 仍须通过行为证明门。

`scope.md` 是可从事实源重生成的覆盖快照：开工时生成，事实源或范围改变时重生成，宣布完成前再生成并逐项对账；中途只回填覆盖依据，重生成发现的新项一律回到 `未处理`。

### `memory/{topic}.md` 的长期内容

每条 Memory 只保存一个未来仍影响判断、而代码/git 不能还原的主题，至少说明：结论、适用边界、依据类型（用户决定 / 外部观察 / 可重跑证明）、证据或复核方式、需要重访的条件。代码已经表达的实现机制不复制进来。

开始工作时只按主题检索相关 Memory，不遍历整个目录；用户决定直接作为当前约束，外部观察在当前环境复核后再采用，可重跑证明直接重跑。当前用户的新决定和当前真实证据可以使旧 Memory 失效，发现冲突先停下判断，不静默选一条。

Memory 默认一个主题一份文件，不设全局 `memory/index.md`；只有主题变大且出现独立读者与边界时才拆目录并增加该主题入口。
